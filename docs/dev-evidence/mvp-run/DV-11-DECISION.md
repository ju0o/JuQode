# DV-11 — 터미널 줄을 무엇으로 구현할 것인가 (PM 판정용)

PM 요청: 세 선택지의 트레이드오프 요약. **파이프 셸 쪽으로 결론 나면 GO 처리**.

이 문서는 판정 재료를 한 장으로 모은 것이다. 실측 원본은
[`DV-11-PIPE-SHELL-SPIKE.md`](DV-11-PIPE-SHELL-SPIKE.md) 이고, 여기서 새로 잰 숫자는 없다.

## 1. 무엇이 요구되어 있고, 지금 무엇이 있는가

`15` TD-01 이 요구하는 것:

| 항목 | 요구 |
|---|---|
| **Inputs** | Quick Command 자연어 입력칸 **· 셸 명령줄** |
| **Primary Action** | **type a command** |
| **Displayed Information** | shell in project cwd · 상시 안전 고지 한 줄(닫을 수 없다) |
| **Unavailable State** | `터미널을 열 수 없습니다.` + 이유 + 대체 경로 두 개 |

`19` §C4 가 그 입력칸의 범위를 못박는다:

> Terminal input scope … **default = user-typed commands run as the user, no filtering pretence**
> (honest about `07` §2) · 터미널 입력은 사용자가 사용자로 실행하는 것으로 화면에 명시

`19` §C6 REC-010 이 프로세스 모델을 적는다: 프로젝트당 하나 · cwd = 프로젝트 루트 ·
첫 열기에서 지연 생성 · **서랍을 닫아도 살아 있어 맥락이 보존됨** · 프로젝트 바뀌면 종료.

**지금 구현된 것: Quick Command 뿐이다.** `app/main/qc/run.js` 는 셸 없이
`spawn(program, args)` 로 규칙 6종의 고정 명령만 실행한다(D-106). **셸 명령줄은 없다.**
`13` §11 의 DoD 는 터미널을 포함한다. 즉 DV-11 은 "개선"이 아니라 **미구현 MVP 요구**다.

## 2. 세 선택지

| | 얻는 것 | 잃는 것 | 이 런에서 검증 가능한가 |
|---|---|---|---|
| **node-pty** | 진짜 터미널 — `/dev/tty` · 색 · 순서 · 작업 제어 | 네이티브 모듈(Electron 버전마다 재빌드) · **이 저장소의 능력 격리 검사가 금지한다** · Windows ConPTY 미검증 | **아니오** |

## 3. 결정적인 실측 하나

```
/dev/tty 직접 접근 ................ NO_DEV_TTY
isatty ............................ NOT_A_TTY
stdin 으로 질문에 답하기 .......... 된다 (종료 0)
stdin 이 닫혀 있을 때의 질문 ...... 멈추지 않는다, 빈 답을 받는다
```

`sudo` · `ssh` · git 자격증명 프롬프트는 **stdin 을 읽지 않는다.** `/dev/tty` 를 직접 연다.
파이프 셸에는 그것이 없다.

그래서 결과는 "멈춰서 사용자를 기다린다"가 **아니다**. 사용자가 답할 기회조차 없이
**빈 답을 받고 실패한다.** 이것이 파이프 셸 선택의 실제 비용이고, 요약하면:

> 파이프 셸에서 `sudo`/`ssh`/자격증명 프롬프트는 **물어보지도 못하고 실패한다.**

---

## 4. 파이프 셸로 GO 할 경우 — 함께 가야 하는 조건

이것은 조건부가 아니라 **동반 요구**다. 빠지면 GO 가 원칙 위반을 만든다.

1. **제품이 그 한계를 화면에서 말해야 한다.** `sudo`/`ssh`/자격증명 프롬프트는 이 터미널에서
   답할 수 없다는 것을, 사용자가 그 명령을 치기 전이나 실패한 직후에 알아야 한다.
   말하지 않으면 D-114 의 **확인 못함**을 제품이 **실패**로 위장하는 셈이 된다.
2. **실패를 실패로 그리지 않는다.** 원인은 사용자의 명령이 아니라 터미널의 능력 한계다.
   `16` §2.1 에서 빨강은 실패 전용이므로, 이 상태는 빨강이 아니라 `지금 안 됨` 계열이다.
   (WBS-33 배너에서 이미 같은 판단을 했다 — 배치 32.)
3. **색 없음과 순서 근사도 고지 대상이다.** stdout/stderr 는 두 파이프라서 실제 순서로
   합쳐지지 않는다. 출력 순서가 뒤바뀔 수 있다는 사실을 숨기지 않는다.
4. **줄 사이 상태는 유지해야 한다.** `cd` 는 줄마다 새 셸이면 사라진다(실측 `LOST`).
   `19` §C6 REC-010 이 요구하는 "닫아도 살아 있는 세션"과 같은 요구다 — 장수 셸 하나에
   줄을 흘려보내는 구조여야 하고, 줄마다 spawn 하는 구조는 요구를 만족하지 못한다.

## 5. node-pty 를 고를 때의 비용 — 저장소 관점

`tests/unit.test.js` 의 능력 검사에 `node-pty` 가 **NEVER 목록**으로 들어 있다.
빌드에 들어가서는 안 되는 것들과 같은 줄이다:

```
'node-pty', 'openExternal', 'execSync', 'eval(', 'new Function',
'better-sqlite3', 'nodeIntegration: true', 'webSecurity: false',
```

즉 node-pty 를 고른다는 것은 **보안 검사를 고쳐야 한다**는 뜻이다. 그 자체가 신호다 —
이 저장소는 네이티브 모듈 없이 만들어졌고, Electron 버전마다 재빌드가 필요한 의존성을
MVP 에 들이는 결정은 패키징(WBS-33)과 Windows 검증(D-125)을 동시에 무겁게 만든다.

## 6. 아직 재지 않은 것 — GO 문서에 그대로 남길 것

- **Windows.** ConPTY 도, Windows 의 파이프 셸도 재지 않았다. 이 문서의 어떤 줄도 Windows 에
  적용된다고 말하지 않는다.
- **Electron 안에서.** 스파이크는 순수 Node 에서 돌았다. Electron 메인 프로세스에서 같은
  결과가 나오는지는 별개의 측정이다(같을 가능성이 높지만, 높다는 것은 측정이 아니다).
- **node-pty 를 실제로 들여 본 것.** 능력 격리 검사가 금지해서 시도하지 않았다.

## 7. 권고

**파이프 셸.** 이유는 얻는 것이 많아서가 아니라, 세 선택지 중 **유일하게 이 런에서 검증
가능하면서 `15` TD-01 의 Primary Action 을 실제로 구현하는 것**이기 때문이다.
mock 은 요구를 미구현으로 남기고, node-pty 는 이 런에서 검증할 수 없다.

단 §4 의 네 조건과 함께여야 한다. 특히 1번 — **말하지 않는 파이프 셸은 파이프 셸보다 나쁘다.**

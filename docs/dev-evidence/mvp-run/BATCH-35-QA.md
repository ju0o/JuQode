## 1. 죽인 것 넷

| 뮤턴트 | 무엇이 망가지나 | 무엇이 잡나 |
|---|---|---|
| `if (id === 'work')` → `!==` | 모호함 카드의 두 읽기가 **라벨을 맞바꾼다**: 규칙 읽기가 `Claude Code 작업으로 보내기` 가 되고 Work 읽기는 `work` 라고 적힌다 | 카드의 버튼 목록을 **라벨로** 단언 (텍스트로만 읽고 있었다) |
| `one.rules.find((x) => x.id === id)` → `!==` | 읽기를 고르면 **고르지 않은 규칙**의 available·reason·data 가 실린다. 카드는 "개발 서버를 꺼 달라는 요청" 이라 말하면서 `npm run dev` 를 실행할 명령으로 들고 있게 된다 | 읽기를 실제로 **눌러** 보고, 그 카드가 자기 규칙의 이유(`지금 안 됨` + not_running)를 말하는지 |
| `listed.rules.find((x) => x.id === 'qc.dev.stop')` → `!==` | 실행 중 카드의 **멈추기 버튼**이 정지가 아닌 규칙을 연다. `실행` 을 누르면 끄려고 연 카드가 서버를 **시작한다** | 버튼을 눌러 나온 카드가 pid + SIGTERM 문장을 담고, **스크립트 본문은 담지 않는지**(그건 시작 카드가 보여 주는 것이다) |
| `r.state === 'failed' ? ' rec' : ''` → `!==` | 실패 카드의 재실행이 복구 동작 표시를 잃고, **성공한** 실행의 재실행이 그것을 얻는다 | 양쪽 모두 — 실패 카드에는 있고 성공 카드에는 없다 |

**한 번 틀렸다.** 멈추기 카드에 `npm run dev` 가 없어야 한다고 단언했는데, **제품이 옳았다**:
그 카드는 신호를 보낼 프로세스를 `pid 129778, npm run dev` 로 가리킨다. 두 카드를 실제로
가르는 것은 **스크립트 본문**이다 — 시작 카드가 승인받으려고 보여 주는 것이고 정지 카드에는
없다. 단언을 그것으로 바꿨다.

## 2. 다섯 번째는 동등 뮤턴트가 아니었다

배치 34 는 `r.reason === 'already_running' && r.data?.pid` → `||` 를 **동등해 보인다**고 적고
"관찰 가능한 차이를 못 찾았다" 고 남겼다. 찾았다.

카드는 **스냅샷**이고, 확인 시점에 `ipc.js` 가 availability 를 다시 묻는다. 거절되면
렌더러는 `{...r, available: false, reason: started.detail}` 로 바꾸는데 — **`data` 는 설명
시점의 것이 그대로 남는다.** 정지 카드의 data 에는 pid 가 있다.

그래서 설명과 확인 **사이에 서버가 죽으면**:

| | `&&` (지금) | `||` (뮤턴트) |
|---|---|---|
| 거절 카드 | `지금 안 됨 · 실패 아님` + `JuQode 가 켠 개발 서버가 지금 없어요` | 같은 문장 **+ `pid 129778`** |

즉 뮤턴트는 **"그 서버는 지금 없어요" 라고 말하면서 그 서버의 pid 를 함께 보여 준다.**

e2e 가 그 경로를 실제로 만든다: 서버를 켜고 → 정지 카드를 띄우고 → **앱 밖에서** 그 pid 를
죽이고(크래시가 하는 그대로) → 앱이 알아챌 때까지 기다린 뒤 → 낡은 카드의 `실행` 을 누른다.
실측:

```
BEFORE: … JuQode 가 켠 개발 서버 프로세스(pid 129778, npm run dev)에 종료 신호(SIGTERM)를 …
AFTER : 지금 안 됨 · 실패 아님 | JuQode 가 켠 개발 서버가 지금 없어요. …   ← pid 없음
```

**덤으로 얻은 것:** `19` §C4 의 "설명과 확인은 두 번의 왕복" 과 `ipc.js` 의 "카드를 믿지 않고
확인 시점에 다시 묻는다" 가 이제 검사된다. 그 경로에는 검사가 하나도 없었다.

## 3. 부수적으로 확인한 것 — `rec` 클래스에는 CSS 가 없다

`btn ... rec` 는 렌더러 네 화면에서 15번 쓰이는데 **어떤 스타일시트도 `.rec` 를 정의하지
않는다.** 복구 동작을 마크업에서 표시할 뿐 화면에서는 아무 차이가 없다.

지금 고치지 않는다 — 색을 주는 것은 `16` §2.1 의 색 문법에 걸리는 디자인 결정이고, 지우는
것은 네 화면에 걸친 변경이다. **적어 두고 다음 배치로 넘긴다.** 이번 단언은 여전히 유효하다:
어느 동작이 복구 동작인지에 대한 **제품 자신의 진술**이 뒤집히는 것이 뮤턴트이고, 그 진술은
마크업에 있다.

### 4.1 도달 불가였던 것 둘, 그리고 그 처리

**`sc03` 의 `cannot-scope` 분기 — 삭제했다.** 화면이 `허용하고 다시 해 보기` 를 그릴지는
스냅샷의 `scopable` 이 정하고, 그 값은 `session.allowSpec(denial, cwd)` 다. 눌렀을 때
supervisor 가 거절하는 조건도 **같은 함수, 같은 인자**다. 두 계산이 다를 수 없으므로 그
분기는 실행될 수 없었고, 출력하려던 문장은 여섯 줄 위 `scopable === false` 가 이미 그린다.
**실행되지 않는 조건 안에 뮤테이션 사이트가 둘 있었다.** 둘이 다를 수 있게 되는 날의 정답은
두 번째 메시지가 아니라 권위 하나다.

**`sc02` 의 presence staleness 가드 — 순수 함수로 뺐다.** `fillPresence` 는 두 번 await 하고
그 사이에 사용자가 떠날 수 있다. 그 상태(느린 저장소가 **네비게이션 뒤에** 답하는 것)는
브리지를 스텁하지 않고는 e2e 로 만들 수 없다 — `hasEvidenceGap` 과 같은 패턴으로
`presenceIsStill(state, project)` 을 내보내고 `tests/presence.test.js` 가 네 조합을 고정한다.
같은 가드가 두 곳에 복제돼 있던 것도 하나가 됐다. **추출로 새로 생긴 사이트 3개도 측정했다** —
빼면서 사이트를 숨기지 않는다.

### 4.3 하나짜리 읽기면으로는 읽기면을 검사할 수 없다

sc04 의 세 뮤턴트가 첫 시도에서 **살아남았다.** 단언을 썼는데도 죽지 않아서 열어 보니,
probe 가 `if (groups().length > 1)` 뒤에 있었고 이 런의 SC-04 는 **그룹이 하나**였다 —
`groupsFrom` 이 설명되지 않은 변경을 한 덩어리로 모은다. 내가 쓴 단언 셋이 한 번도 실행되지
않았고, **원래 있던 `secondOn` 검사도 같은 이유로 이미 공허했다.**

고친 것: 설명 패스 픽스처가 **두 그룹**(파일 하나씩)을 돌려준다. 고르기 · Raw 토글 · 카드
클릭 대상을 설명된 읽기면에서 누른다. 그리고 두 자리 모두 **그룹 개수를 단언**한다 —
건너뛰는 대신 터지도록.

> 조용히 건너뛰는 길이 검사는 검사가 아니다. 이 배치에서 그것을 두 번 봤다 — 하나는 물려받은
> 것이고 하나는 내가 만든 것이다.

### 4.4 단언 하나가 또 틀렸다

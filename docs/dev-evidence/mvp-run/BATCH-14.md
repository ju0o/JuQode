## WBS-36 — 밝은 테마가 AA 를 통과하지 못하고 있었다

`21` WBS-36 의 Tests 열이 **토큰 대비비 단위 테스트**를 이름으로 요구한다. 그게 없었다.
e2e 가 기본 버튼 하나의 대비를 재고 있었고, 나머지 토큰은 아무도 재지 않았다.

써서 재 보니 **밝은 테마가 깨져 있었다.**

| 토큰 | 표면 | 대비 | |
|---|---|---|---|
| `--mut2` | `--card` | **3.11 : 1** | AA 미달 |
| `--mut2` | `--board` | **2.72 : 1** | 큰 글자 3 : 1 기준에도 미달 |
| `--part` · `--wait` | `--board` | 4.40 : 1 | AA 미달 |
| `--part` · `--wait` | `--grey` | 4.44 : 1 | AA 미달 |

어두운 테마도 둘이 미달이었다 — `--mut2` on `--card2` (4.15) · on `--grey` (3.94).

`--mut2` 는 장식용 회색이 아니다. **제품이 실제로 읽히기를 바라는 문장들**이 그 등급으로
그려진다 — Presence 카드의 `진행 정도를 뜻하지 않아요`, 취소 버튼의 부속 문장, 기록 카드의
`끝난 작업은 사라지지 않아요`. 2.72 : 1 은 그 문장들을 읽을 수 없다는 뜻이다.

### 고치면서 다른 것을 깨뜨리지 않기

`--mut2` 를 AA 까지 올리면 `--mut` 쪽으로 밀린다. 그 상태로 두면 **가독성 실패를 위계 실패로
바꾼 것**뿐이다. 그래서 `--mut` 도 함께 내렸다:

| | 이전 | 이후 | card 대비 |
|---|---|---|---|
| light `--mut` | `#5d6672` | `#4c545f` | 5.82 → 7.66 |
| light `--mut2` | `#8a93a0` | `#646d7a` | 3.11 → 5.24 |
| light `--part` · `--wait` | `#b45309` | `#ad4f08` | 5.02 → 5.39 |
| dark `--mut2` | `#79838f` | `#8a94a1` | 4.54 → 5.68 |

테스트가 **둘 다** 검사한다 — 모든 텍스트 토큰이 놓일 수 있는 모든 표면에서 4.5 : 1 이고,
동시에 네 개의 텍스트 등급이 서로 **1.15 : 1 이상 떨어져 있고 순서대로**다. 한쪽을 다른 쪽의
대가로 지불할 수 없다.

### 무엇을 재고 무엇을 재지 않는가

제품이 실제로 그리는 조합만 잰다. 중립 텍스트 넷 × 중립 표면 넷, 그리고 상태 색 각각 ×
중립 표면 넷 + **자기 자신의 배경**. 복구 초록을 실패 배경 위에서 재는 것은 팔레트를 측정하는
게 아니라 **지시하는** 것이다.

### 붉은색은 실패 하나뿐

`16` §2.1 의 규칙을 토큰 파일에 대고 검사한다. 첫 초안은 "r 채널이 가장 크다" 로 잡았고
**amber 를 빨강이라고 신고했다** — 정확히 `16` §2.1 이 막으려는 혼동이다. 색상(hue)으로 다시
썼다: 빨강은 0° ± 15°, amber 는 25–35°. 회색은 hue 가 아니라 **채도**로 제외한다 — 거의
무채색인 값도 hue 는 있고 그건 아무 뜻이 없다.

그리고 검사가 자기가 본다고 주장하는 차이를 실제로 보는지 함께 확인한다 — `--part` 가
15°~60° 안에 있는지.

### 이미 되어 있던 것

`16` §2.1 의 **amber FILL(부분) vs amber OUTLINE(대기)** 구별은 WBS-29 가 이미 두 테마 모두에서,
칩과 실제 표면 양쪽에서 재고 있다. 토큰 파일은 그 둘이 **같은 색이어야** 한다는 쪽을 지킨다 —
색을 갈라놓아서 "고치면" 문법이 깨진다.

다섯 표면 × 두 테마 스크린샷도 이미 있다(SC-01 · SC-02 · SC-03 · SC-04 · TD-01).

### 설정 화면이 없다

D-135 의 명시된 범위 위반이다. `renderer.js` 에 `SC-05` · `settings` · `설정` 어느 것도 없고,
`screens/` 에 설정 파일이 없고, 토글은 상단 바의 버튼 셋(`밝게` · `어둡게` · `시스템`)이다.

## WBS-38 — JuQode 의 권유가 Agent 의 선언처럼 보이지 않게

`17` 이 표로 적어 둔다:

| | NEXT | 다음 행동 |
|---|---|---|
| 누가 | Claude Code 가 선언한 다음 Step | JuQode 가 주는 선택지 |
| 신호 없으면 | **비어 있다** (D-107) | 그대로 있다 |
| 시각 처리 | Step 목록 · 슬롯 | 카드 아래 **버튼** |

절대 규칙: **두 요소는 같은 시각 처리를 쓰지 않고, 다음 행동이 NEXT 슬롯을 채우지 않는다.**

`C.next.label` · `C.next.gloss` 는 `18` 에 있었지만 **아무도 쓰지 않고 있었다.** 다음 행동은
라벨 없는 `row-acts` 버튼 줄로 그려지고 있었다 — 사용자가 Agent 가 선언한 일과 구별할 근거가
화면에 없었다.

### 셋으로 갈라 놓는다

1. **목소리.** `16` 의 배우 색을 그대로 쓴다 — 다음 행동은 JuQode 청록(`--juq`), NEXT 슬롯은
   Claude 보라(`--claude`). 새로 만든 규칙이 아니라 디자인 시스템에 이미 있는 뜻이다.
2. **모양.** 다음 행동은 버튼이고, NEXT 는 텍스트다. **NEXT 슬롯 안의 컨트롤은 사용자가
   Claude 가 "말한" 것을 누르는 것**이 된다.
3. **말.** 블록이 소리 내어 말한다 — `18` `next.gloss`: JuQode가 드리는 선택 — Claude Code가
   알린 일이 아니에요.

### 구조로 막는다

`nextActions(buttons)` 에는 **선언된 Step 을 건넬 방법이 없다.** 매개변수가 `buttons` 하나뿐이고,
`step` · `declared` · `snap.` 어느 것도 코드에 없다. 규율이 아니라 구조다 — 테스트가 시그니처와
코드(주석 제외)를 둘 다 확인한다.

NEXT 슬롯은 한 군데서만 만들어지고, 그 안에 `btn(` 이 없다는 것을 블록 단위로 확인한다.

### 화면에서 잰다

e2e 가 **두 테마 모두**에서 두 블록의 계산된 스타일을 읽는다: 왼쪽 강조선 색이 다르고, 라벨
색이 다르고, 슬롯의 버튼 수가 0 이고, 다음 행동의 버튼 수가 1 이상이고, 슬롯 텍스트가 `NEXT`
로 시작하고 `다음 행동` 을 포함하지 않는다.

그리고 `17` 표의 **두 번째 행**을 실측한다 — 이 Work 는 다음 Step 을 선언하지 않았으므로
슬롯은 `Claude Code가 아직 다음 단계를 보내지 않았어요.` 이고, **다음 행동은 그대로 있다.**

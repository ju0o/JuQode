## 고친 것 둘 — 둘 다 시간에 관한 것이다

### `확인 불가` 가 프로젝트에 영원히 들러붙었다

`orientationOf` 가 `works.some(w => w.outcome === 'ended_unknown')` 였다. 노트북을 한 번 닫아서
Work 하나가 재조정되면, 그 뒤로 열 개를 정상적으로 끝내도 SC-02 는 계속
`이전 작업이 지금 어떤 상태인지 확인할 수 없어요` 라고 말한다 — 완료된 Work 들이 그 문장 아래
줄지어 있는 채로. `18` 이 이 문장을 **단수**로 쓴 이유가 있다. 사용자가 방금 떠나온 그 하나에
대한 문장이다. 이제 `works[0]` 만 본다.

### History 의 "최신순" 이 결정론이 아니었다

`order by started_at desc` 뿐이었다. `started_at` 은 밀리초 해상도 ISO 문자열이라 **같은
밀리초에 시작한 Work 둘은 동점**이고, 동점이면 SQLite 는 어느 쪽을 먼저 줘도 된다. 그래서
기록의 순서가 실행마다 달라졌고, `works[0]` 을 읽는 방향 문장도 같이 흔들렸다.

이건 픽스처만의 이야기가 아니다 — 빠른 재시도는 실제로 같은 밀리초 안에 들어간다.
`rowid desc` 를 동점 처리로 붙였다(삽입 순서).

**이 두 개는 서로를 가리고 있었다.** 기존 방향 테스트는 "하나 재조정된 뒤 정상 종료한 Work 가
있으면 finished" 를 이미 요구하고 있었는데, 순서가 무작위라 절반쯤 통과했다. 순서를 고정하고
나서야 방향 규칙이 틀렸다는 것이 매번 드러났다.

## 뮤테이션

| 뮤턴트 | 결과 |
|---|---|
| `orientationOf` 를 `some` 으로 되돌리기 | killed |
| `unknown` 을 아예 안 내기 | killed |
| 빈 목록 처리 제거 | killed |
| 재조정 안 하기 / `interpreted` 로 닫기 / 답을 지우기 | 3/3 killed |
| `rowid` 동점 처리 제거 | **처음엔 SURVIVED** |
| 오래된 것부터 정렬 | killed |

`rowid` 동점 처리를 지워도 테스트가 통과했다 — 기존 테스트들이 충돌을 *운으로* 만들고 있었을
뿐이기 때문이다. 타임스탬프를 **일부러 같게 만드는** 테스트를 넣고서야 죽었다. 이 런에서
반복해서 나온 그 모양이다: 가장 중요한 성질을 지킨다는 테스트가 실패할 수 없는 상태.

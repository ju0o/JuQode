## HIGH-1 · `확인됨` 도구 실행 수가 두 가지 이유로 적게 나오고 있었다

결과 카드에 `JuQode가 지켜본 도구 실행 N` 이 **확인됨** 칩과 함께 나간다. 그 N 이 이렇게
계산되고 있었다:

```js
const toolResults = signals.filter((s) => s.kind === KIND.TOOL_RESULT).length;
```

**① 신호를 세지 블록을 세지 않았다.** `user` 메시지 하나가 `tool_result` 블록을 **여러 개**
실을 수 있다(병렬 도구 호출). `toSignal` 은 그걸 신호 **하나**로 만들고 `payload.all` 에 전부
담는다. 리듀서의 `toolsUsed` 는 이미 `all.length` 를 더하도록 고쳐져 있었는데 — 결과 경로는
아니었다.

**② 읽기가 500행에서 잘린다.** `repo.signalsFor` 의 기본 상한이다. 긴 Work 의 도구 수가 **자기
역사가 얼마나 읽혔는지에 따라** 달라졌다.

적게 나오는 확인된 수는 수가 없는 것보다 나쁘다. 칩이 확인해 보라고 말하고 있기 때문이다.

**고친 방식:** `build()` 는 이제 신호 목록을 **받지 않는다.** 세는 것은 호출자의 일이고,
`repo.countToolResults()` 가 전체 역사에 대해 블록 단위로 센다. 호출자가 세지 않았으면
`toolResults` 는 `null` 이고 **주장을 아예 하지 않는다** — 짐작한 수에 확인됨 칩을 다는 대신.

### 그리고 첫 수정이 틀렸다 — e2e 가 잡았다

`countToolResults` 의 첫 판은 `JSON.parse(payload)?.all` 을 읽었다. 단위 테스트가 통과했다.
**앱에서는 아무것도 안 바뀌었다.**

supervisor 가 저장하는 것은 리듀서의 payload 가 아니라 **CLI 의 원본 줄**이다
(`writeSignal(..., { payload: line })`). 그래서 실제 행에는 `all` 이 없고 블록은
`message.content[]` 안에 있다. 단위 테스트는 내가 만든 모양을 넣고 내가 만든 모양을 읽고 있었다.

잡은 것은 e2e 의 **교차 확인**이다: 화면의 수를, 앱 자신이 기록한 신호를 독립적으로 세어
비교한다. 그리고 **그 교차 확인의 첫 판도 같은 실수를 했다** — `all` 을 읽어서 3이 아니라 2를
셌다. 둘 다 원본 줄을 읽도록 고쳤고, 단위 테스트는 이제 **두 모양을 다** 넣는다.

기록해 둔다: **자기가 만든 픽스처만 읽는 단위 테스트는 저장 형식을 검증하지 않는다.**

### 픽스처가 이제 병렬 호출을 담는다

e2e 의 녹화에 병렬 `tool_result` 가 없었으면 `blocks === rows` 라 이 검사가 버그와 수정을
구별하지 못한다. 그래서 녹화에 **한 메시지에 두 블록**을 넣었고, 검사가 그것을 **먼저 확인한다**:

```
assert.ok(t.blocks > t.rows, '이 검사는 버그를 구별할 수 없다')
```

검사가 검사할 수 있는 상태인지를 검사한다.

## HIGH-2 · 부분 완료 카드가 목록 하나만 그리고 있었다

`15` 부분 완료는 **된 것**과 **안 된 것** 둘 다 요구한다. 된 것 목록은 증거 쌍에서만 왔고,
렌더러가 `if (done.length && notDone.length)` 로 그렸다. 그래서 **증거 쌍이 판정하지 못하면
된 것 제목 자체가 사라졌다.**

안 된 것만 있는 부분 완료 카드는 **"한 건 없다" 로 읽힌다.** 아무도 하지 않은 주장이다.
D-114: 침묵은 확인 못함이지 사실이 아니다.

`verify()` 는 이걸 내내 신고하고 있었고 `buildChecked` 는 기록에 적는 것밖에 못 했다 —
화면은 계속 목록 하나를 그렸다. 이제 **부분 결과면 제목을 항상 그리고**, 잴 수 없었으면 그
아래에 `18` 자신의 단어로 **확인 못함** 칩을 놓는다.

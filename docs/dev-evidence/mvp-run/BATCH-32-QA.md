# Batch 32 — WBS-33: 서명되지 않은 빌드라고 말한다

PM 이 다음 큐로 지정한 WBS-33 잔여 작업. 요구는 두 문서가 같은 말로 적고 있다.

> **`21_WBS.md`** WBS-33 위험 열 — 서명 인증서 없음 → **서명되지 않은 빌드임을 표시(숨기지 않음)**
> **`22_MASTER_TRACEABILITY.md`** §95 — 서명 인증서가 없으면 서명되지 않은 빌드임을 표시한다 —
> **숨기지 않는다는 제품 원칙의 배포 측면.** (`19` §D1 · 원칙 2 · `13` §8)

## 착수하자마자 나온 문제 — 이 문장에 화면이 없다

`15_SCREEN_SPEC.md` SC-01 의 `Displayed Information` 은 제품 소개 한 문장과 최근 목록뿐이다.
빌드에 대한 사실은 없고, `Explicit Not Included` 도 그것을 배제하지 않는다 — **포함도 배제도
되어 있지 않다.** `14` 의 Top bar 는 프로젝트 범위이고 SC-02/03/04 에만 있다. `18` 에는
`서명` 이 들어간 키가 하나도 없다.

**CANON_FINDINGS CF-21** 로 기록했다. Canon 을 고치지 않고, 요구는 구현하고, 배치 결정과
근거를 거기 남겼다.

## 색이 정해져 있지 않았고, 문법상 쉬운 답도 없었다

`16` §2.1 에서 쓸 수 있는 토큰을 지워 나가면 남는 것이 거의 없다.

| 토큰 | 뜻 | 쓸 수 있나 |
|---|---|---|
| `--fail` 빨강 | **화면에서 유일한 빨강**, 실패 전용 | **아니오** — 서명 안 됨은 실패가 아니다 |
| `--part` 앰버 채움 | 부분 완료 | 아니오 |
| `--wait` 앰버 외곽선 | 대기 | 아니오 |
| `--rec` 초록 ▸ | 복구 행동 | 아니오 — 사용자가 할 행동이 없다 |
| `--unk` 파선 | 확인 못함 | **판정 못했을 때만** |
| `--juq` 청록 | JuQode 자신의 목소리 | **예 — 판정했을 때** |

그래서 이것은 **한 상태가 아니라 두 상태**다. D-114 어휘에서 다르고 `16` 문법에서도 다르다.

## 판정은 무엇을 읽고 하는가 — PE 인증서 테이블

빌더 로그는 빌드가 **의도한 것**을 말하고, 파일은 **실제인 것**을 말한다. 검증 하네스가
`Get-AuthenticodeSignature` 로 PE 인증서 테이블을 읽는 것과 같은 근거를 앱도 읽는다.

**spawn 하지 않는다.** 인증서 테이블은 PE Optional Header 의 데이터 디렉터리 4번 항목, 8바이트다
(RVA 4 + SIZE 4). 우리 자신의 파일에 있는 사실을 알기 위해 부팅 때 PowerShell 자식 프로세스를
띄우는 것은 **더 비싸면서 덜 확실한 방법**이다. `fs.read` 로 수십 바이트면 끝난다.
PE32 와 PE32+ 는 데이터 디렉터리 시작 위치가 다르다(96 vs 112) — 둘 다 읽는다.

### 서명되었다고는 절대 말하지 않는다

인증서 테이블에 바이트가 있다는 것은 **유효하고 신뢰되고 만료되지 않은 서명**이라는 뜻이
아니다. 그것을 판정하려면 인증서 체인과 OS 신뢰 저장소가 필요하고 이 코드는 그걸 읽지 않는다.

| 읽은 것 | 상태 | 화면 |
|---|---|---|
| 인증서 테이블 SIZE = 0 | `unsigned` — **확인됨** | 청록 · `서명되지 않은 빌드예요` |
| SIZE > 0 | `unknown` — **확인 못함** | 파선 · `이 빌드가 서명되었는지 확인하지 못했어요.` |
| 잘린 헤더 · PE 아님 · 못 읽음 | `unknown` | 파선 |
| 패키징 안 됨 (개발 실행) | `not-applicable` | **아무것도 안 그림** |
| — | `signed` | **어떤 입력으로도 나오지 않는다** |

`not-applicable` 이 유일한 침묵이다. `npm start` 는 배포되는 빌드를 만들지 않으므로 아직
고지할 사실 자체가 없다. **확인 못함일 때 침묵하는 것은 모른다는 사실을 숨기는 것**이고,
그것은 사실 자체를 숨기는 것과 같은 실패다.

### 가장 위험한 오답 하나

읽기 버퍼는 0으로 채워져 있다. 그래서 **인증서 테이블 앞에서 끝나는 파일**은 빈 인증서
테이블과 **바이트가 같다**. 여기서 `서명 없음` 이라고 답하면 확신에 찬 오답이 된다.
실제로 읽은 바이트 수를 확인하고 `truncated-header` 로 물러난다 — 테스트로 고정했다.

## 어디에, 어떻게

- **호스트: SC-01.** 설치 직후 처음 보는 화면이고, 프로젝트 문맥이 없는 유일한 화면이다.
  Windows 경고(SmartScreen)를 막 지나온 직후가 이 사실이 의미를 갖는 시점이다.
- **전달: `juqode:boot`.** SC-01 이 이미 기다리는 응답이다. 별도 채널이면 화면이 고지 없이
  한 번 그려진 뒤 움직이게 되는데, 그건 어느 쪽 답보다도 나쁘다. 값은 **항상 온다** —
  없을 수 있는 필드였다면 화면이 세 가지 경우를 다뤄야 하고 그중 하나를 틀린다.
- **문구: `gap.`** `18` 에 키가 없으므로 승인된 사전 항목인 척하지 않는다.
- **조용하게.** 이 화면의 주 행동은 폴더 열기다. 고지가 소리치면 그것과 경쟁한다.
  숨기지 않는다는 것은 **있으라는 뜻이지 크라는 뜻이 아니다.**

## 테스트

e2e 가 이 상태를 찍으려면 문제가 하나 있었다 — 소스 실행은 `app.isPackaged` 가 false 라
고지에 **도달할 수 없다.** 그래서 답을 흉내내는 대신 **파일을 바꾼다**:
`JUQODE_SIGNATURE_EXE` 가 가리키는 합성 PE 를 실제로 파싱한다. 스크린샷은 하드코딩된
문자열이 아니라 **바이트를 읽은 결과**다.

| | |
|---|---|
| unit | `# tests 556 · # pass 556 · # fail 0` |
| `tests/signing.test.js` | PE32 · PE32+ · SIZE=0 · SIZE>0 · 잘린 헤더 · PE 아님 · 너무 짧음 · 없는 파일 |
| 절대 조건 | 받아들이는 **어떤 입력으로도** `signed` 가 나오지 않는다 (테스트로 고정) |
| e2e (측정값) | `titleColor rgb(99,207,220)` = `--juq` · `--fail` 은 `#f08b8b` — **빨강 아님을 픽셀에서 측정** |
| e2e (확인 못함) | 저장소 거부 앱을 인증서 있는 픽스처로 띄워 `dashed` · `확인하지 못했어요` · **확실한 문장을 빌려 쓰지 않음**을 확인 |
| 렌더 증거 | `docs/dev-evidence/screens/sc01-light.png` · `sc01-dark.png` (두 장만 갱신) |

CSS 소스 검사도 넣었다: `.buildnote` 블록이 `--fail`/`--part`/`--wait`/`--rec` 를 **쓰지
않는다**는 것. 주석은 제거하고 검사하므로, 빨강이 아닌 이유를 설명하는 주석이 검사를
통과시키지 못한다.

## 확인 못함

- **진짜 서명된 빌드로는 확인하지 않았다.** 인증서가 없다 — `19` §V 가 서명을 NOT VALIDATED
  로 두는 이유 그대로다. `SIZE > 0` 경로는 합성 PE 로만 실행됐다.
- **실제 패키징된 exe 에서의 `app.getPath('exe')`** 도 Windows 재실행 때 확인해야 한다 (DV-16).

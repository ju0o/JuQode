## BLOCKER — "도구를 하나도 주지 않는다" 가 거짓이었다 (제품 B2 · 기술 B2 · 애드버서리 B1)

```js
const NO_TOOLS = [];                                   // explain.js
session.run({ ..., allowedTools: NO_TOOLS, ... })
if (allowedTools.length) args.push('--allowedTools', ...allowedTools);   // session.js
```

빈 배열은 **플래그를 아예 안 붙인다.** 측정된 argv:

```
-p --output-format stream-json --verbose --session-id 0aea…
```

설명 패스가 사용자 프로젝트 디렉터리에서 **CLI 기본 도구 전부**를 들고 돌고 있었다. 주석은
"파일을 고치지 못한다" 고 적혀 있었다. `19` §S 가 Change Group 프롬프트에서 `.env` 류를 빼 두는
것도, 도구를 든 패스가 파일을 직접 읽으면 그냥 우회된다.

**`--allowedTools` 는 허용 목록이지 금지 장치가 아니다.** 빌트인 도구 집합을 비우는 건
`--tools ""` 다. 일회용 스크래치 디렉터리에서 **측정**했다(실제 프로젝트 아님):

> Claude Code 2.1.266 · `--tools ""` 로 파일 수정을 요청 → 텍스트 턴만 나오고
> (`Read (No such file or directory)`), `permission_denials: []`, 1 턴, **대상 파일 바이트 동일.**

이제 `session.run({ tools })` 로 붙이고, 유닛 테스트가 **실제로 나가는 argv** 를 검사한다.
e2e 픽스처도 `--tools` 를 보고 분기해 설명 응답을 준다 — 플래그가 사라지면 두 곳에서 죽는다.

## BLOCKER — 증거가 조용히 틀렸다 (기술 B1) · 이번 배치가 만든 회귀

`git add` 가 읽지 못하는 파일을 만나면 **인덱스를 쓰지 않고** 128 로 끝난다. 배치 06 의
관용 조건은 `addFailed && !staged.length` 였는데, 인덱스는 사용자 인덱스의 **복사본**이라
tracked 파일이 있는 저장소에서는 절대 비지 않는다. 그래서:

```
before ref  1bef487d…
after  ref  1bef487d…   ← 같다
changedPaths []          ← 방금 고친 파일이 없다
```

`바뀐 파일이 없어요 ✓확인됨`. **직전까지는 throw 해서 EVIDENCE_GAP 으로 남던 것을, 이번 배치가
조용한 거짓 부정으로 바꿨다.** 이제 실패 시 `firstUnreadable()` 로 유해한 원인을 직접 찾고,
찾으면 거부한다(메시지를 읽지 않는다 — 이 기계는 한국어로 출력한다). 무해한 원인(gitignore
안내)은 그대로 통과하고, 경고는 basis 에 실려 나간다.

## BLOCKER — 변경 없음(확인됨)을 non-Git 프로젝트에 대고 말했다 (제품 B1)

diff 를 만드는 basis 는 `git_tree` 뿐이다. `saveDiffs` 가 아무것도 안 쓰면 SC-04 는 빈 상태로
가는데, 그 문장은 **(확인됨)** 을 달고 있다. SC-03 이 한 클릭 전에 `변경 3개` 라고 말한
Work 에 대해서다. 이제 `readerFor` 가 `changes()` 에 물어보고, 답을 모르면 `unknown` 으로
표시한다 — `12` 에는 "확인 못했다" 상태가 있고 반대를 말하는 상태는 없다.

## 애드버서리 — 뮤턴트 29개 중 20 생존

가장 아픈 셋:

- **`pre.innerHTML = f.patch` 가 유닛 · e2e 를 모두 통과했다.** 픽스처 패치에 마크업이 없었을
  뿐이다. 주석은 "never parsed as markup" 이라고 적혀 있었고 아무것도 강제하지 않았다.
  이제 렌더러 파일에서 `innerHTML` 에 `''` 외의 값을 대입하면 유닛 테스트가 죽는다.
- **`sc04.js` 전체가 아무것도 렌더하지 않아도 유닛 스위트가 초록이었다.** e2e 가 유일한 방벽인데
  그 e2e 는 `groups.every(g => !g.explainable)` 로 픽스처를 **실패 상태에 고정**하고 있었다 —
  WBS-26 성공 경로 전체가 어떤 테스트에서도 실행되지 않았다.
- **`readerFor` 의 "저장된 묶음" 가지가 죽어 있었다.** 그 가지를 무시하는 뮤턴트가 살아남았고,
  그건 사용자가 설명 받기를 눌러 성공해도 화면이 영원히 설명 못함으로 남는다는 뜻이다.

셋 다 닫았다: e2e 픽스처가 `--tools` 를 보고 진짜 묶음을 돌려주므로 **설명된 상태**(JUQODE 칩 ·
무엇/왜/어떤 동작에 · confidence 칩 · 저장된 묶음 경로)가 처음으로 실행되고 스크린샷도 남는다.
`readerFor` 는 유닛 테스트 6개를 받았다.

## 스위트 자체의 결함 — 이게 제일 컸다

애드버서리가 부수적으로 보고했다: **20회쯤 돌리면 `/tmp` 에 `juqode-*` 디렉터리 5,991개 ·
836 MB 가 쌓이고 tmpfs 쿼터에 걸린다.** 여덟 개 테스트 파일이 각자 `process.on('exit')` 로만
정리하는데, 죽거나 중단된 런은 그걸 실행하지 않는다.

**측정된 결과: 스위트가 매번 다른 자리에서 깨지는 50% flake.** "N tests pass" 라는 주장이 전부
무의미해지고, flaky 스위트는 뮤턴트도 조용히 죽인다. 이 세션에서는 셸 자체가 죽기도 했다 —
뮤테이션 사본 다섯 개(각각 node_modules 포함)가 디스크를 채워 `true` 조차 실행되지 않았다.

`tests/tmp.js` 하나로 합치고, **매 런이 시작할 때 이전 런이 남긴 것을 쓸어낸다** — 정리가 이
프로세스가 정상 종료하는지에 의존하지 않는다. 이후 loop 스위트 flake **0/10**.

## 그리고 flake 를 쫓다 찾은 진짜 결함 (CF-14)

flake 를 추적하다 별개의 것을 찾았다. D-126a 는 증거 기준을 **사용자 인덱스의 복사본**으로
만들라고 한다. 복사본은 **stat 캐시**를 함께 물려받고, `git add -A` 는 그 캐시를 믿는다 —
크기가 같은 편집이 기준과 같은 타임스탬프 구간에 떨어지면 **다시 읽지 않는다.**

실제 supervisor 경로로 Work 300회씩 측정:

| 인덱스 | 놓친 횟수 |
|---|---|
| **빈 인덱스에서 시작** | **0 / 300** |
| 복사 + mtime 을 epoch 로 (재읽기 강제 시도) | 4 / 300, 다른 픽스처에서는 **옛 내용**을 트리에 썼다 |

빈 인덱스로 바꿨다. 캐시가 없으면 틀릴 캐시도 없다. 사용자의 `.git/index` 를 건드리지 않는다는
D-126a 의 목적은 그대로다. 부작용 두 개(tracked+gitignored 파일 제외 · `rm --cached` 가 지금은
잡을 게 없음)는 CF-14 에 적었고, 테스트는 어느 단계가 돌았는지가 아니라 **사후 조건**을 본다.

간헐 결함이라 동작으로는 회귀를 잡을 수 없으므로, `capture()` 가 다시 사용자 인덱스를 읽으면
죽는 **구조 테스트**를 뒀다.

## 시각 QA — 그리고 조용히 실패하던 식별자

설명된 상태 스크린샷에서 헤더에 **`[object Observable]`** 이 떠 있었다. `when(at)` 이 정의도
import 도 없이 호출됐는데 **throw 하지 않았다** — 브라우저에 전역 `when` 이 있어서 Observable 을
돌려준 것이다. 자유 식별자가 플랫폼 전역으로 해석되면 조용히 실패하고 **데이터처럼 보인다.**

`brief.js` 의 `when` 을 export 해서 import 했고, e2e 는 이제 **어느 화면에서든** 텍스트 노드에
`[object …]` 가 있으면 죽는다.

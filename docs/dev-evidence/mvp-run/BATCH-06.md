## WBS-26 — 이 패키지의 위험은 **과잉 주장** 하나다

`21` 이 위험 칸에 `overclaiming` 이라고 적어 둔 유일한 패키지다. 그래서 모듈을 둘로 갈랐다.

- `groupsFrom(response, {diffs, signals})` — **순수 함수**. 모델이 뭐라 했든, JuQode 가 가진
  사실과 대조해서 사실을 이길 수 없는 묶음만 돌려준다. WBS-26 인수 조건 셋이 전부 여기에
  있고, CLI 도 네트워크도 모델도 없이 테스트가 닿는다.
- `explain(db, workId, …)` — 읽기 전용 패스를 돌리고 살아남은 것만 저장한다.

세 규칙, 그리고 각각을 죽인 뮤턴트:

| 인수 조건 | 구현 | 뮤턴트 |
|---|---|---|
| 모든 change_group 이 실제 raw_diff 를 인용한다 | 인용된 경로를 `raw_diff` 행 id 로 해석한다. 해석 안 되면 그 인용은 사라지고, 인용이 하나도 안 남은 묶음은 묶음이 아니다. 한 diff 의 주인은 하나뿐이다(D-121) | `e1-ghostfile` · `e2-emptygroup` · `e3-dupowner` |
| `확인됨` 은 관측된 실행 결과가 있을 때만 | `work_signal` 에 `tool_result` 가 있을 때만 `confirmed` 가 살아남고, 그때 근거 신호를 `sourceRef` 로 적는다. `tool_use` 만 있는 건 관측된 결과가 아니다. D-114 어휘 밖의 단어는 전부 `expected` | `e4-noDowngrade` · `e5-alwaysDowngrade` · `e6-toolUseCounts` · `e7-badVocab` |
| 설명 실패 시 `설명 못함` — 이유를 만들지 않는다 | 거부·크래시·침묵·JSON 아님이 전부 같은 자리로 간다. `why` 는 `null`, `what` 도 `null`, confidence 도 없음. 패스가 그냥 건너뛴 파일도 여기로 모인다 | `e8-noUnexplained` · `e9-inventWhy` |

프롬프트는 **diff 텍스트를 건네고 도구를 하나도 주지 않는다**. 이미 끝난 Work 를 설명하는
패스가 그 프로젝트를 고칠 수 있으면 그건 읽기가 아니다. 그리고 패스는 사용자가 `이 변경
설명 받기` 를 누를 때만 돈다 — 화면에 들어온 부작용으로 자식 프로세스를 띄우지 않는다.

테스트에 넣고서야 죽었다.

## WBS-28 — SC-04

`15` SC-04 의 세 칸: 뜻 → 코드 → 원문. 좁은 창에서도 그 순서로 접힌다 — 작은 화면이 문법을
먼저 보여 주면 이 화면의 논지가 뒤집힌다.

Canon 문구는 전부 `18` §SC-04 **그대로**다. 처음 초안은 `15` 의 서술을 옮겼는데, `15` 는 화면을
설명하고 `18` 이 문구다. 둘이 다르면 `18` 이 이긴다. 사전에 키가 없는 것(Raw Diff 닫기 ·
설명 받기 · 파일 n개 · 잘림 안내)은 `gap:` 에 표시해 두었다 — 승인된 문구인 척하지 않는다.

인수 조건:

- **Code Block 없음(단위화 불가) → Raw 로만 도달 가능** — D-118 의 건너뛰기. `Raw Diff 보기` 가
  **묶음** 카드에 있고, 단위화 못한 파일 카드에도 `▸ 원문으로 보기` 가 있다. e2e 가 코드 단위를
  거치지 않고 원문 텍스트에 닿는 것을 실제로 확인한다.
- **표시 불가 diff(바이너리 · >1 MiB) → 바이너리 카드** — 회색, 붉은색 없음(12 §16).
- **change_group 이 하나도 없음 → 빈 상태가 오류로 보이지 않음** — 설명 패스가 아직 안 돈 Work 는
  `설명 못함` 묶음 하나로 읽힌다. 그 모양은 `groupsFrom(null, …)` 이 만든다. **파생이지 기록이
  아니다** — 읽기가 쓰기를 하면 호출자가 전부 놀란다.

## e2e — 그리고 거기서 나온 진짜 결함

SC-04 을 e2e 에 넣으려면 픽스처가 **실제로 파일을 바꿔야** 했고, diff 가 나오는 basis 는
`git_tree` 뿐이라 seed 프로젝트를 진짜 git 저장소로 만들었다. 그러자 바로 터졌다.

> **측정됨 (git 2.53.0):** pathspec 에 `:(exclude)` 원소가 **하나라도** 있으면 `git add` 는
> ignore 된 파일을 **명시적으로 지목된 것**으로 취급하고 1 로 끝난다 —
> `다음 경로는 .gitignore 파일 중 하나 때문에 무시합니다: .env` — 그러면서 인덱스는 정확하게
> 쓴다. 같은 트리에서 `git add -A -- .` 는 0 으로 끝난다.

즉 **자기 `.env` 를 gitignore 하는 프로젝트에서는 basis 를 아예 못 잡았다.** 실제 프로젝트의
평범한 모양이다. 지금까지 픽스처에 `.gitignore` 가 하나도 없어서 유닛 테스트가 볼 수 없었다.

`-f` 는 답이 아니다 — ignore 된 파일을 스테이징하는 것이야말로 D-126a 가 막으려는 것이다.
advice 를 꺼도 상태는 안 바뀐다(측정). 그래서 **상태를 어느 쪽으로도 믿지 않고 산출물을
확인한다**: add 가 문제를 보고했고 인덱스가 비었으면 진짜 실패이므로 거부하고, 인덱스가
있으면 기존 검증(`ls-files` → `rm --cached` → 트리)이 판단한다. 실패 사유는 버리지 않는다.

회귀 테스트 2개, 뮤턴트 2개 모두 killed.

e2e 픽스처도 정직해졌다: 이제 `--resume` 을 보고 **허용된 턴에서** 파일을 고친다 — 거부당한
Edit 이 곧 수행하는 Edit 이다(D-133 계약 B). 영원히 거부하는 픽스처로는 거부 카드밖에 그릴
수 없었다.

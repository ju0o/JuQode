## 3. 부분 UNIQUE 인덱스 — **이미 되어 있습니다**

### 지적
> 한 프로젝트에 `is_current = true`인 해석이 여러 개, 종료 안 된 작업이 여러 개 생길 수 있다. 부분 UNIQUE 인덱스가 필요하다. 해석 교체는 트랜잭션으로 처리하라.

### 실제
**둘 다 이미 있습니다.** `app/main/db/schema.sql`:

```sql
create unique index interpretation_one_current on interpretation(project_id) where is_current;
create unique index work_one_active_per_project on work(project_id) where status <> 'ended';
```

트랜잭션도 이미 그렇게 되어 있습니다 (`repo.js saveInterpretation`) — 기존 `is_current` 끄기와 새 행 넣기가 `begin`/`commit` 한 덩어리 안에 있습니다.

### 그럼 왜 이런 지적이 나왔나 — **제 실수입니다**

처음 만든 DBML에는 이 조건이 `Note`로 적혀 있었습니다. 그런데 **"Note를 빼 달라"**고 하셔서 전부 지우면서, 이 정보가 같이 사라졌습니다. 리뷰어는 다이어그램만 보고 "없다"고 판단한 것이고, 그 판단은 다이어그램만 놓고 보면 옳습니다.

> **쉽게 말하면:** 집에 잠금장치는 멀쩡히 달려 있는데, 도면에서 그 표시를 지워버린 겁니다. 도면만 본 사람은 "문이 안 잠기는데요?"라고 할 수밖에 없습니다.

### 어떻게 대응하나
DBML은 **부분 인덱스(`where` 조건이 붙은 인덱스)를 표현하는 문법 자체가 없습니다.** 그래서 셋 중 하나를 골라야 합니다.

| 방법 | 장점 | 단점 |
|---|---|---|
| **A. 이 세 곳만 Note를 되살린다** | 다이어그램을 보는 사람에게 바로 보임 | Note를 빼 달라고 하신 뜻과 어긋남 |
| **B. `//` 주석으로 적는다** | 코드에는 남음 | 다이어그램 화면에는 **안 보임** |
| **C. 별도 문서(`ERD.md`)에만 적는다** | DBML이 깨끗함 | 다이어그램만 받은 사람은 또 같은 지적을 함 |

**제 추천은 A입니다.** Note를 빼자고 하신 건 "설명이 장황해서"였는데, 이건 설명이 아니라 **DB가 실제로 강제하는 규칙**이고 문법으로 표현할 방법이 없습니다. 해당 3개 테이블에만 한 줄씩 붙이는 정도입니다.

## 1. 로컬 DB ↔ 서버 DB — **맞습니다. 지금 정하는 게 가장 쌉니다**

### 지적
> `project.owner_id → profile.id`는 진짜 외래키가 아니다. 서버는 로컬이 보낸 `owner_id`를 믿으면 안 된다. 토큰에서 사용자 ID를 확인하고 등록된 장치인지도 검증하라.

### 실제
**맞습니다.** 이미 DBML에 주석은 달아 뒀습니다:

```
// logical link across two databases: project lives in local SQLite, profile in Postgres.
// not enforced by a foreign key.
```

하지만 리뷰어 지적의 **진짜 핵심은 다이어그램이 아니라 보안**입니다.

> **쉽게 말하면:** 회원증 번호를 손님이 직접 적어서 내는 상황입니다. "저 3번 회원이에요"라고 종이에 써서 내면, 가게는 그걸 그대로 믿고 3번 회원 적립을 해 줍니다. 남의 번호를 적으면 남의 적립이 쌓입니다.
>
> 올바른 방식은 **회원증을 스캔하는 것**입니다 — 손님이 뭐라고 적었든 무시하고, 스캔한 결과로만 판단합니다.

### 어떻게 대응하나

**규칙 하나면 끝납니다: 서버는 클라이언트가 보낸 `user_id`를 절대 읽지 않는다.**

이미 그렇게 설계되어 있긴 합니다 — `consume_work()` 안에서 `auth.uid()`(로그인 토큰에서 서버가 직접 꺼낸 값)를 씁니다. 그래서 지금 설계는 **이 지적에 대해 이미 안전합니다.**

다만 두 가지를 더 해야 합니다.

1. **장치 검증** — `device_id`도 클라이언트가 보냅니다. 그 장치가 *그 사용자의* 등록된 장치인지 서버가 확인해야 합니다. 안 하면 남의 장치 ID를 적어서 감사 기록을 오염시킬 수 있습니다.
2. **다이어그램 표기** — 논리적 연결이라는 걸 주석이 아니라 **눈에 보이게** 표시. (점선으로 그릴 방법이 DBML에 없으므로, 관계선을 아예 빼고 `owner_id` 컬럼에 표시하는 방법도 있습니다.)

## 6. 사용량 중복 집계 — **맞습니다. 이게 가장 급합니다**

### 지적
> `usage_day`는 횟수만 저장하고 어떤 작업 때문에 늘었는지 모른다. 네트워크 재시도로 같은 작업을 두 번 보내면 중복 집계된다. `audit_work`에 `client_work_id`를 추가하고 `(device_id, client_work_id)`를 UNIQUE로.

### 실제
**맞습니다.** 제가 만든 `consume_work()`는 부를 때마다 무조건 +1 합니다.

> **쉽게 말하면:** 지하철 개찰구에서 카드를 찍었는데 화면이 안 떠서 한 번 더 찍었더니 **요금이 두 번 빠진** 상황입니다. 개찰구가 "이 카드 방금 들어왔었지"를 기억하지 못해서입니다.
>
> 해결은 **입장권에 번호를 매기는 것**입니다. 같은 번호로 두 번 오면 두 번째는 무시합니다.

여기서 그 번호가 `client_work_id`입니다 — 로컬 `work.id`(UUID)를 그대로 쓰면 됩니다.

### 한 가지 정정
지적에 "동시에 여러 요청이 들어오면 일일 제한을 넘긴 뒤 작업이 시작될 수도 있다"는 부분이 있는데, **이건 이미 막혀 있습니다.** `consume_work()`가 `for update`로 행을 잠근 뒤 판정하고 올리기 때문에, 동시 요청 20개를 던져도 상한에서 정확히 멈춥니다 (WBS P1-3이 그걸 재는 작업입니다).

막히지 않는 건 **재시도로 인한 중복**뿐입니다. 그건 진짜 구멍이고 고쳐야 합니다.

### 어떻게 대응하나
서버가 아직 없으니 **지금은 스키마만 고치면 됩니다 — 비용 0**:
- `audit_work`에 `client_work_id` 추가
- `(device_id, client_work_id)` UNIQUE
- `consume_work()`가 이 키로 먼저 확인하고, 이미 있으면 **올리지 않고 기존 결과를 그대로 돌려준다**

## 4. 프로세스 추적 — **절반은 있고, 나머지 절반이 지적보다 나쁩니다**

### 지적
> `work`와 `quick_command_run`이 실행 중 상태를 저장하는데 어떤 프로세스인지 알 컬럼이 없다. 실행기 인스턴스 ID · PID · 프로세스 시작 시각 · 앱 세션 ID를 넣어라. PID는 재사용되므로 PID만으로 판단하면 안 된다.

### 실제

**`work` 쪽 — 정보는 있는데 이상한 데 들어 있습니다.**
PID와 시작 시각은 저장됩니다. 그런데 컬럼이 아니라 **`work_signal` 테이블의 JSON 덩어리 안**에 있습니다. 꺼내려면 그 작업의 모든 신호를 순서대로 훑으면서 JSON을 하나씩 파싱해야 합니다 (`repo.js processFor`).

PID 재사용 문제는 **이미 알고 대응하고 있습니다** — `main.js`가 "PID가 응답해도, 그 프로세스의 시작 시각이 작업 시작 시각보다 **앞설 때만** 살아 있다고 믿는다"로 판단합니다. 지적한 위험을 정확히 그렇게 막고 있습니다.

**`quick_command_run` 쪽 — 아무것도 없습니다. 그리고 그 결과가 실제 버그로 이어집니다.**
스키마 주석이 스스로 이렇게 적고 있습니다:

> 「pid 컬럼이 없으므로, 이전 실행에서 시작된 run 은 물어볼 수조차 없다」

그래서 앱을 껐다 켜면, 개발 서버가 **실제로는 돌고 있어도** 무조건 "확인 불가"로 닫힙니다.

> **쉽게 말하면:** 가스레인지를 켜 두고 외출했다가 돌아왔는데, 불이 켜져 있는지 **확인할 방법이 없어서** 일단 "모르겠음"이라고 적어두는 겁니다. 실제로는 계속 타고 있는데요.

### 어떻게 대응하나
1. **`work`**: PID/시작시각을 JSON에서 꺼내 **진짜 컬럼으로** 올린다. (조회가 빨라지고, 무엇보다 스키마를 보면 있다는 걸 알 수 있게 된다.)
2. **`quick_command_run`**: 같은 컬럼들을 **새로** 추가한다. 여기가 진짜 구멍이다.
3. **앱 세션 ID**: 앱이 실행될 때마다 UUID를 하나 만들어 두 테이블에 같이 넣는다. "이전 실행이 남긴 것"과 "지금 실행이 만든 것"을 구분하는 가장 확실한 방법이다.

> **참고**: 지적의 "실행기 인스턴스 ID"와 "앱 세션 ID"는 이 제품에서는 같은 것입니다 — 실행기가 앱 자신이니까요. 컬럼 하나면 됩니다.

## 5. 외부 파일 관리 — **맞습니다. 그리고 실제 누수를 하나 찾았습니다**

### 지적
> `stream_ref` · `unified_ref` · `output_ref` · `evidence_basis.ref`가 외부 파일을 가리키는데, 그 파일의 존재·크기·해시·삭제를 관리하는 테이블이 없다. 공통 파일 테이블을 만들어라.

### 실제 — 네 개가 서로 다른 물건입니다

| 컬럼 | 실제로 무엇인가 | 상태 |
|---|---|---|
| `unified_ref` | 진짜 파일 (`diffs/<sha256>.patch`) | ✅ 쓰이고 있음 |
| `output_ref` | 컬럼은 있는데 **아무도 값을 넣지 않음** | 💀 죽은 컬럼 |
| `stream_ref` | 컬럼은 있는데 **아무도 값을 넣지 않음** | 💀 죽은 컬럼 |
| `evidence_basis.ref` | **파일이 아님** — Git 객체 ID | ℹ️ 다른 종류 |

`evidence_basis.ref`는 파일 경로가 아니라 Git 트리 ID입니다. Git 저장소가 자기 무결성을 스스로 관리하므로 (해시가 곧 내용입니다) 이건 지적 대상에서 빼는 게 맞습니다.

### 그리고 — **지적하지 않은 진짜 문제**

`pruneDiffs()`가 diff 행을 지울 때, **행만 지우고 파일은 남깁니다.** 코드를 보면 지우기 직전에 `unified_ref`(파일 경로)를 읽어오는데, 읽어놓고 **쓰지를 않습니다.**

> **쉽게 말하면:** 서류 목록에서 항목은 지웠는데, 창고에 있는 실제 서류 상자는 그대로 둔 겁니다. 목록에 없으니 아무도 못 찾고, 창고만 계속 찹니다.

작업을 재시도할 때마다 큰 diff 파일이 하나씩 쌓이고, **지워지지 않습니다.**

### 어떻게 대응하나

**단계로 나누는 걸 권합니다.**

1. **지금 (작음)** — `pruneDiffs`가 파일도 지우게 한다. 몇 줄이고, 실제로 새는 걸 막는다.
2. **지금 (작음)** — 죽은 컬럼 둘(`output_ref` · `stream_ref`)을 **살리거나 지운다.** 지금은 "있는데 안 쓰는" 상태라 스키마를 읽는 사람을 속입니다.
3. **나중** — 공통 파일 테이블. 지적대로 만들면 좋지만, **지금 관리할 파일이 사실상 한 종류(diff blob)뿐**이라 테이블을 먼저 만드는 건 이릅니다. `output_ref`를 실제로 쓰기 시작할 때 같이 만드는 게 맞습니다.

## 2. 작업 간 교차 참조 — **맞습니다. 다만 판정이 필요합니다**

### 지적
> `change_group_file`이 `change_group_id`와 `raw_diff_id`를 각각 참조할 뿐, 둘이 같은 `work_id`에 속하는지 확인하지 않는다. 작업 A의 변경 그룹에 작업 B의 diff를 연결할 수 있다. `code_block`도 같다. `(id, work_id)` UNIQUE를 추가하고 복합 외래키로 묶어라.

### 실제
**구조적으로 맞습니다.** DB만 놓고 보면 막는 것이 없습니다.

> **쉽게 말하면:** 병원에서 환자 차트와 엑스레이 사진을 각각 번호로 관리하는데, **"이 차트와 이 사진이 같은 환자 것인가"는 아무도 확인하지 않는** 상태입니다. 실수로 다른 환자 사진을 끼워 넣어도 시스템이 막지 않습니다.

다만 **현재 코드에서는 발생하지 않습니다.** 그룹과 diff를 쓰는 경로가 하나뿐이고, 그 경로가 늘 같은 `work_id`로 씁니다. 즉 **잠재된 결함**이지 지금 나는 버그가 아닙니다.

### 왜 바로 못 고치나
`schema.sql`은 **Canon(JuQode-Private)의 축자 복사본**이고, 이 저장소에서 편집하지 않는 규칙이 있습니다. 이건 마이그레이션 + Canon 변경 요청 건이 됩니다. 어제 이미 4건이 그렇게 쌓였습니다.

### 어떻게 대응하나 — 세 갈래

| 방법 | 내용 | 비용 |
|---|---|---|
| **A. 지적대로 전부** | `(id, work_id)` UNIQUE 추가 → `change_group_file`에 `work_id` 추가 → 복합 FK | 마이그레이션 + Canon 판정 + 테스트. **중간** |
| **B. 테스트로만 막기** | 저장 계층이 교차 조합을 거부하는지 테스트로 고정 | **작음**. 단 DB는 여전히 허용 |
| **C. 지금은 기록만** | Canon 변경 요청표에 올리고 다음 판정 때 함께 | **0** |

**제 추천은 B + C입니다.** 이유는 이 저장소의 기존 방식과 같습니다 — 마이그레이션 2번 주석이 「SQLite는 기존 테이블에 CHECK를 추가할 수 없으므로 제약을 선언하지 않는다; **저장 계층이 같은 모양을 거부하고 테스트가 그것을 고정한다**」고 적고 있습니다. 이미 같은 상황을 그렇게 처리한 전례가 있습니다.

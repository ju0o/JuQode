## 1. 왜 JuQode에 법칙이 필요한가

### 1.1 세 번의 실패에서 배운 것

| 시도 | 무엇을 없앴나 | 왜 실패했나 |
|---|---|---|
| 1 | File Tree 제거 | Feature/Behavior 블록이 그 자리를 차지했다 |
| 2 | 블록 제거 | 점·경로·질량이 그 자리를 차지했다 |
| 3 | 3R.1 (질량/경로) | 도표(diagram)로 읽힌다. 소프트웨어로 읽히지 않는다 |

세 번 모두 **표상을 교체**했지만, 세 번 모두 같은 것이 빠져 있었다.

> **그림에는 법칙이 없었다.**

도표와 소프트웨어의 차이는 선의 모양이 아니다.
**도표는 무엇도 하지 않고, 소프트웨어는 무언가를 한다.**
JuQode 화면이 도표처럼 느껴지는 이유는 그 안의 것들이 **아무 법칙도 따르지 않기 때문**이다.

### 1.2 법칙이 하는 일

법칙은 장식이 아니라 **제약**이다. 좋은 법칙은 다음을 강제한다.

- 이 채널(면적·선·모서리·색)은 **무엇을 의미할 수 있고 무엇을 의미할 수 없는가**
- 새로운 소프트웨어 유형이 나타났을 때 **새 UI를 만들지 않고** 설명할 수 있는가
- 애니메이션 하나를 넣을 때 **그것을 정당화하는 실제 사건**이 있는가

법칙이 이 세 가지를 못 하면 그것은 법칙이 아니라 **브랜딩 문구**다. 그런 것은 이 문서에서 기각했다(§6).

### 1.3 이 문서가 만들지 않는 것 (HARD)

철학자 초상 · 인용구 · 파티클 · 행성 · 진자 애니메이션 · "quantum" 시각 장치 ·
과학 테마 UI · 물리 시뮬레이션 엔진 · 사용자에게 노출되는 "Software Physics"라는 단어.

**사용자는 철학을 읽지 않는다. 철학을 겪는다.**

## 2. Product Philosophy

> **믿음(Belief). 3개.** JuQode가 소프트웨어와 창조에 대해 무엇을 믿는가.

### P1 · BECOMING — 소프트웨어는 완성되지 않는다

**출처:** 과정 철학(Whitehead) · 니체의 생성(Werden). 인용은 하지 않는다.

소프트웨어는 완성을 향해 가는 물건이 아니라 **계속 되어가는 것**이다.
JuQode는 "다 됐다"는 상태를 렌더링하지 않는다.

**강제되는 제품 결정**

| | |
|---|---|
| 완성도 지표 금지 | 진행률 · 퍼센트 · "아키텍처 완성" · 체크리스트 완료율이 **존재하지 않는다** |
| 여백은 패딩이 아니다 | 몸은 **경계를 가득 채우지 않는다.** 남은 공간은 *아직 실현되지 않은 소프트웨어*다 |
| 성장은 확장이 아니라 재정규화 | 질량이 늘면 캔버스가 커지는 게 아니라 **몸 전체가 다시 계산된다.** 스크롤·오버플로가 생기지 않는다 |
| 형태가 이력을 지닌다 | 지금 형태는 지나온 평형들의 결과다 (→ L3) |

**왜 이것이 브랜딩이 아닌가:** "완성도 지표 금지"와 "재정규화"는 구현자가
따르거나 어길 수 있는 검사 가능한 규칙이다. 3R.1의 MASS LAYOUT이 이미 재정규화로 동작한다.

### P2 · ABSORPTION — 복잡함은 JuQode의 것이다

**출처:** Kafka를 **진단 렌즈**로 사용한다. 법칙이 아니다.

카프카적 상황이란 *자기가 만든 것에 자기가 소외되는 상태*다.
현대 개발은 실제로 그렇다 — 파일 · 폴더 · 브랜치 · 빌드 · 권한 · 환경변수 ·
의존성 관리자 · 설정 · CI · Git · 배포 · 로그.

바이브 코더는 **자기가 만든 소프트웨어의 관료제에 압도당한 창조자**다.

> **그 복잡함은 사라지지 않는다. 다만 그것을 누가 지느냐가 제품 결정이다.**
> JuQode가 진다.

**강제되는 제품 결정**

| | |
|---|---|
| Primary UI 어휘 금지 | 파일 · 폴더 · 브랜치 · 커밋 · PR · 환경변수 · 컨테이너 · 스키마 · 엔드포인트 |
| 그 어휘가 사는 곳 | **DEEP / Evidence 안에서만.** 사용자가 요청했을 때만 |
| 번역 의무 | JuQode는 기술 사실을 **숨기지 않고 번역**한다. 숨기면 P3 위반이다 |
| 실패 모드 | "쉬운 IDE"는 어휘를 그대로 두고 버튼만 키운다. 그건 흡수가 아니다 |

### P3 · HONESTY — 모르는 것은 모르는 채로 남는다

**출처:** 인식론. 그리고 이 저장소가 이미 내린 결정 —
`Evidence에 UNKNOWN 상태` · `Evidence over Agent Claims`([docs/README.md](../README.md)).

**강제되는 제품 결정**

| | |
|---|---|
| `UNKNOWN`은 1급 상태다 | 실패도 성공도 아닌 **정당한 종착 상태**. 침묵하거나 추측으로 바꾸지 않는다 |
| 에이전트의 주장 ≠ 사실 | 확인되지 않은 변경은 확인된 변경과 **다르게 그려진다** (→ L4, E2) |
| 가짜 움직임 금지 | 실제 사건이 없으면 아무것도 움직이지 않는다 (→ §13) |
| 모르는 영역을 발명하지 않는다 | 해석 못 한 저장소에 그럴듯한 구조를 그려 넣지 않는다 (→ §12) |

**세 믿음의 관계:** P1은 *무엇을 보여줄 것인가*, P2는 *무엇을 감출 것인가*,
P3은 *감춘 것을 어떻게 정직하게 표시할 것인가*를 정한다. P2와 P3은 서로를 견제한다.

## 3. Software Physics Canon

> **행동(Behavior). 5개.** 소프트웨어가 JuQode 안에서 어떻게 움직이는가.
> 각 법칙은 §15 번역표 11항목을 전부 통과했다. 통과 못 한 것은 §6에서 기각했다.

### 채널 배타성 규칙 (이 Canon의 반(反)노이즈 장치)

> **하나의 법칙은 하나의 시각 채널만 소유한다.**

| 법칙 | 소유 채널 | 이 채널을 다른 법칙이 쓸 수 없다 |
|---|---|---|
| L1 MASS | **면적 · 위치** | 중요도를 색으로 표현하지 않는다 |
| L2 CAUSALITY | **선 · 방향 · 경계 통과** | 관계를 인접(proximity)으로 암시하지 않는다 |
| L3 EQUILIBRIUM | **렌더링 자체의 안정성** | 작업 중을 스피너로 표현하지 않는다 |
| L4 UNCERTAINTY | **모서리 품질 · 내부 채움** | 확신을 뱃지·아이콘으로 표현하지 않는다 |
| L5 OBSERVATION | **해상도** | 확대를 라벨 추가로 표현하지 않는다 |
| E1 REVERSIBILITY | **경계 기준 위치 + 색** | **색은 오직 결과와 상태만 의미한다. 범주는 절대 아니다** |

이 표 하나가 "인포그래픽이 되는 것"을 구조적으로 막는다.
**범주는 위치와 면적을 얻고, 색은 얻지 못한다.**

### L1 · MASS — 의미가 자리와 크기를 만든다

| | |
|---|---|
| **Inspiration** | 뉴턴 역학의 질량. **인력(引力) 시뮬레이션은 차용하지 않는다**(§6에서 기각) |
| **Actual Meaning** | 모든 의미 객체는 질량을 가진다. 질량은 **의미론적**이며 파일 수가 아니다 |
| **Product Principle** | 배치는 저작이 아니라 **계산**이다. 아무도 좌표를 손으로 정하지 않는다 |
| **Visual Behavior** | 질량 → band/lane 두께(3R.1 §3.2), 밀도 → 표식 밭. **무게중심**이 몸의 성격을 만든다 |
| **Interaction Behavior** | 무거운 곳이 먼저 눈에 들어온다 = **어디를 Qode할지가 라벨 없이 결정된다** |
| **Qode Behavior** | Qode는 질량을 바꾼다. 질량이 바뀌면 실루엣이 바뀐다 (3R.1 §14) |
| **Evidence Behavior** | 증거는 질량을 바꾸지 않는다. **확신(L4)만 바꾼다.** 채널 배타성 |
| **User Value** | "내 소프트웨어가 어느 쪽으로 무거운지"를 읽는 능력. 파일 목록으로는 절대 안 되는 일 |
| **Misuse Risk** | 질량을 LOC·파일 수로 계산하면 **거짓말이 된다.** 30줄 결제 로직이 3,000줄 CSS보다 무겁다 |
| **Verdict** | **KEEP** |

**질량의 정의 (v0.1 구현 계약)**

```
mass = f(의존 피참조 수, 변경 위험, 최근 사용/관심, 외부 접촉 여부, 사용자 명시 중요도)
mass ≠ g(줄 수, 파일 수, 함수 수)
```

파일 수는 질량의 **입력 중 하나도 아니다.** 상관관계가 있을 뿐이며,
상관을 인과로 쓰면 P3 위반이다.

**무게중심(center of mass)** 은 1급 읽을거리다.
`무게중심이 아래로 내려갔다` = 이 소프트웨어는 데이터 중심이 되었다.
`무게중심이 경계 쪽으로 갔다` = 이 소프트웨어는 대부분 바깥과 닿아 있다(인프라·통합).

### L2 · CAUSALITY — 모든 것은 어디선가 와서 어딘가로 간다

| | |
|---|---|
| **Inspiration** | 인과율. 물리이자 철학 |
| **Actual Meaning** | 소프트웨어는 정적인 집합이 아니라 **방향을 가진 변환**이다 |
| **Product Principle** | 변경은 "이게 바뀌었다"가 아니라 **"이게 바뀌어서 저기까지 닿는다"** 로 표현된다 |
| **Visual Behavior** | 경로(Path)와 방향. **경계를 통과하는 경로 = Port**. 자기에게 되돌아오는 경로 = Loop |
| **Interaction Behavior** | 구조를 선택하면 **닿는 범위(reachable set)** 가 함께 밝아진다. 애니메이션이 아니라 상태다 |
| **Qode Behavior** | Qode의 결과는 변경점 + **전파 범위**. Change Story가 여기서 나온다 |
| **Evidence Behavior** | 전파 주장에는 증거가 붙는다. 증거 없는 전파는 `UNKNOWN`으로 남는다 |
| **User Value** | 비개발자가 가장 못 하는 질문 — **"이거 바꾸면 뭐가 같이 망가져?"** 에 답한다 |
| **Misuse Risk** | 순식간에 **플로차트**가 된다. 모든 함수 호출을 그리면 끝장이다 |
| **Verdict** | **KEEP (제약 필수)** |

**인과의 제약 (없으면 플로차트가 된다)**

```
전파 깊이 기본값 = 2         그 너머는 "더 있음"으로만 표시하고 그리지 않는다
전파는 경계에서 멈춘다        Port를 넘어가면 JuQode의 앎이 끝난다 (→ E1)
경로는 의미 단위다            함수 호출이 아니라 사람이 말할 수 있는 이동
```

**이 법칙이 Backend-only를 구원한다.** Feature가 하나도 없어도
`들어온다 → 변한다 → 갈라진다 → 쌓인다/나간다`는 **인과만으로 완전히 읽힌다.**

### L3 · EQUILIBRIUM — Qode는 작업이 아니라 평형 사이의 이동이다

**이 Canon에서 가장 강한 법칙이다.** IDE·에이전트 도구와 JuQode를 가르는 지점이 여기다.

| | |
|---|---|
| **Inspiration** | 동역학의 안정 상태. **진자의 운동이 아니라 진자가 멈추는 지점** |
| **Actual Meaning** | 소프트웨어는 안정 상태에 머문다. Qode는 한 안정 상태에서 다음 안정 상태로의 **이행**이다 |
| **Product Principle** | **"코드가 써졌다"는 완료가 아니다.** 확인되기 전까지 평형은 회복되지 않았다 |
| **Visual Behavior** | 안정 = 렌더링이 고요하다. 교란 = **영향받는 영역만** 안정성을 잃는다. 전역 스피너 없음 |
| **Interaction Behavior** | 되돌리기 = "실행 취소"가 아니라 **이전 평형으로 돌아가기**. 사람의 말로 표현된다 |
| **Qode Behavior** | §9의 6-상태 기계. `SETTLING`이 존재한다는 것 자체가 이 법칙의 산물 |
| **Evidence Behavior** | **증거만이 `SETTLING`을 `SETTLED`로 바꾼다.** 시간 경과로는 안 된다 |
| **User Value** | "다 됐다는데 진짜 된 거야?" — 바이브 코더의 가장 큰 불안에 구조로 답한다 |
| **Misuse Risk** | 사용자에게 "평형"이라는 단어를 보여주는 것. **절대 노출하지 않는다** |
| **Verdict** | **KEEP** |

> **다른 도구들은 코드가 써진 순간 초록 체크를 준다.
> JuQode는 그 순간을 `SETTLING`으로 붙잡아 둔다. 그것이 정직이다.**

**Software Time의 재정의 (§10에서 확장)**

Software Time의 점은 커밋이 아니라 **평형**이다. `SETTLED` 상태만 시간축에 점을 찍는다.
확인되지 않은 변경은 시간축에 존재하지 않는다 — 돌아갈 수 있는 곳이 아니기 때문이다.

### L4 · UNCERTAINTY — 앎은 부분적이다

**이 법칙의 이름은 원래 ENTROPY였다. 기각하고 개명했다. 이유는 §7에 명시한다.**

| | |
|---|---|
| **Inspiration** | 인식론. 그리고 지도학의 *조사 신뢰도(survey reliability)* 표기 |
| **Actual Meaning** | JuQode가 소프트웨어에 대해 아는 것은 부분적이며, 부분마다 확신이 다르다 |
| **Product Principle** | 확신은 **선의 성질**로 표현한다. 뱃지·아이콘·경고 배지로 표현하지 않는다 |
| **Visual Behavior** | 아래 3단계 표 |
| **Interaction Behavior** | 불확실한 곳을 선택하면 **"무엇이 있으면 확실해지는가"** 를 말한다. 경고만 하지 않는다 |
| **Qode Behavior** | Qode 대상이 불확실하면 JuQode는 **먼저 그것을 말하고** 진행 여부를 사람에게 넘긴다 |
| **Evidence Behavior** | 증거가 확신을 올린다. 이 법칙의 전부다 |
| **User Value** | "여긴 내가 확실히 아는 부분, 여긴 아닌 부분"의 구분. 비개발자가 스스로 판단할 근거 |
| **Misuse Risk** | **뱃지 수프.** 화면이 노란 삼각형으로 뒤덮이면 실패다 |
| **Verdict** | **KEEP (개명 + 노출 제약 필수)** |

**확신의 3단계 — 이것이 전부다. 4단계로 늘리지 않는다.**

| 상태 | 모서리 | 내부 | 의미 |
|---|---|---|---|
| **확인됨** | 실선 hairline | 표식 밭 정상 | 증거가 있다 |
| **미확인** | 파선 | 표식 밭 정상 | 있다고 보지만 확인 안 됨 |
| **모름** | 파선 `--ink4` | **내부를 그리지 않는다** | 무언가 있으나 안을 모른다 |

`모름`의 표현이 핵심이다. **윤곽은 있고 내부는 비어 있다** —
"여기 무언가 있지만 나는 그 안을 모른다"가 라벨 없이 읽힌다.
이 표현 하나가 §12의 *해석 못 한 저장소* 케이스를 해결한다.

**노출 제약 (뱃지 수프 방지 — 이 제약이 없으면 이 법칙은 기각이다)**

> **불확실성은 그것이 지금 하려는 일과 관련될 때만 표면화된다.**
> 기본 화면에서 확신은 렌더링되지 않는다. 다음 세 경우에만 나타난다:
> ① Qode 대상이 그 영역일 때 ② 사용자가 그 영역을 선택했을 때
> ③ 방금 바뀐 것이 아직 확인되지 않았을 때(`SETTLING`)

**v0.1 축소:** 3단계를 다 만들지 않는다. **`모름` 하나만** 구현한다(§15).

### L5 · OBSERVATION — 주의가 해상도를 정한다

| | |
|---|---|
| **Inspiration** | **지도학의 일반화(cartographic generalization).** 양자역학이 *아니다* — §7 참조 |
| **Actual Meaning** | 무엇을 보고 있느냐가 무엇이 해상되는지를 결정한다 |
| **Product Principle** | Semantic Zoom의 철학적 근거. 확대는 배율이 아니라 **의미 해상도**의 변화다 |
| **Visual Behavior** | 3R.1 §10 + CONSTANT INK RULE. 잉크 총량 일정, 해상도만 변화 |
| **Interaction Behavior** | Context를 설정하지 않는다. **보고 있는 곳이 곧 Context다**(3R.1 §11 C) |
| **Qode Behavior** | 의미적 위치가 자동으로 Qode 대상 범위가 된다 |
| **Evidence Behavior** | **관측은 사실을 만들지 않는다.** 확대해도 모르는 것은 여전히 모른다 (P3) |
| **User Value** | 한 번에 하나만 본다. 1,000개 파일 프로젝트에서도 화면이 조용하다 |
| **Misuse Risk** | ① 확대가 라벨 추가가 되는 것(이전 프로토타입의 실패) ② 유사 양자역학 브랜딩 |
| **Verdict** | **KEEP (양자 프레이밍은 기각)** |

**관측의 부수 효과 — 아키텍처 결정**

> **관측되지 않은 것은 계산하지 않는다.**

이것은 시각 규칙이 아니라 **엔지니어링 규칙**이다.
JuQode는 저장소 전체를 미리 파싱하지 않는다. FAR에서는 FAR에 필요한 만큼만 안다.
그래서 1,000 파일 저장소에서도 첫 화면이 빠르고, **모르는 상태가 정직하게 기본값**이 된다.

L4와 L5가 여기서 만난다: **관측하지 않은 영역은 `모름`이다.** 발명하지 않는다.

## 4. Ethical Laws

> **통제(Control). 2개.** 결과가 큰 행동을 JuQode가 어떻게 다루는가.

### E1 · REVERSIBILITY — 경계 밖으로 나간 것은 되돌릴 수 없다

**이 Canon에서 가장 실용적인 발견이다.**

3R.1은 BOUNDARY를 "이것이 하나의 Software다"라는 뜻으로 정의했다.
Canon은 여기에 **두 번째 의미**를 부여한다.

> **경계선은 되돌릴 수 있음(reversibility)의 경계선이다.**
> 경계 안에서 JuQode는 이전 평형으로 되돌릴 수 있다.
> 경계를 넘어간 것은 되돌릴 수 없다.

| | |
|---|---|
| **Inspiration** | 행위 윤리. 결과에 대한 책임 |
| **Actual Meaning** | Port는 "연동"이 아니라 **비가역성이 발생하는 지점**이다 |
| **Product Principle** | **결과가 저항을 정한다.** 저항은 모달이 아니라 **몸에서** 먼저 표현된다 |
| **Visual Behavior** | 비가역 행동은 **경계를 넘어가는 경로**로 그려진다. 색은 여기에만 쓰인다 |
| **Interaction Behavior** | 실행 전에 **넘어갈 경계와 그 너머의 대상**이 먼저 보인다 |
| **Qode Behavior** | 아래 3단계 저항 표 |
| **Evidence Behavior** | 저항이 높을수록 **사전** 증거를 요구한다(dry-run·영향 범위). 사후 증거로는 부족하다 |
| **User Value** | 비개발자가 가장 무서워하는 것 — 모르고 큰일 내는 것 — 을 구조가 막는다 |
| **Misuse Risk** | 확인 모달 남발. 모든 것에 저항을 걸면 사용자는 전부 무시하게 된다 |
| **Verdict** | **KEEP** |

**저항 3단계**

| 등급 | 판정 | 저항 |
|---|---|---|
| **가역** | 경계 안 · 이전 평형으로 복귀 가능 | 없음. 그냥 한다. 되돌리기만 보장 |
| **비가역** | 경계를 넘음 (외부 호출·전송·게시·과금) | **넘어갈 경계와 대상을 먼저 그린다** + 사람의 확인 |
| **파괴적** | 경계 밖 + 복구 불가 (운영 데이터 삭제·권한 변경·자격증명 노출) | 위 + 사전 증거 + **의도의 재진술** |

**"의도의 재진술"** 은 체크박스가 아니다.
사용자가 *무엇이 일어날지를 자기 말로* 확인하게 한다. 클릭 습관으로 통과할 수 없어야 한다.

**v0.1 주의:** v0.1에는 실제 비가역 행동이 거의 없다.
그래도 **데이터 모델에 등급 필드를 지금 넣는다.**
이 저장소의 기존 규칙과 같다 — *기능은 미루되 구조는 미루지 않는다*([docs/README.md](../README.md)).

### E2 · EVIDENCE — 주장은 사실이 아니다

| | |
|---|---|
| **Inspiration** | 인식론 + 이 저장소의 기존 결정 `Evidence over Agent Claims` |
| **Actual Meaning** | 에이전트가 "했다"고 말한 것과 확인된 것은 **다른 상태**다 |
| **Product Principle** | 증거만이 확신을 올리고, 증거만이 평형을 회복시킨다 |
| **Visual Behavior** | `SETTLING`(미확인)과 `SETTLED`(확인)는 **다르게 렌더링된다** |
| **Interaction Behavior** | 결과 화면은 항상 **무엇으로 확인했는지**에 도달할 수 있다 |
| **Qode Behavior** | 증거 없는 Qode는 완료되지 않는다. `SETTLING` 또는 `UNKNOWN`에 머문다 |
| **Evidence Behavior** | 이 법칙 자체 |
| **User Value** | 사용자가 에이전트를 **믿을지 말지 스스로 정할 근거**를 갖는다 |
| **Misuse Risk** | 아무것도 확인되지 않아 전부 `SETTLING`에 남으면 제품이 쓸모없어진다 |
| **Verdict** | **KEEP (완화 필수)** |

**완화 규칙:** `UNKNOWN`은 **행동 가능**해야 한다.
"확인 못 했다"로 끝내지 않고 **"무엇이 있으면 확인되는가"** 를 항상 함께 말한다.
그렇지 않으면 정직함이 무력함이 된다.

## 5. 법칙들은 어떻게 결합하는가

법칙은 독립적이지 않다. **결합에서 제품이 나온다.**

```
        P1 BECOMING ──────────┐
                              ↓
   L1 MASS  ×  L3 EQUILIBRIUM   →   성장은 평형 사이의 형태 변화다
                                     (카드 추가가 아니다)

   L2 CAUSALITY × E1 REVERSIBILITY → 경계를 넘는 인과 = 비가역 행동
                                     (Port가 윤리적 의미를 갖는다)

   L4 UNCERTAINTY × L5 OBSERVATION → 관측하지 않은 것은 모름이다
                                     (게으른 분석이 정직한 기본값이 된다)

   L3 EQUILIBRIUM × E2 EVIDENCE   →  증거만이 평형을 회복시킨다
                                     (SETTLING 상태의 존재 이유)

        P3 HONESTY ───────────┘
```

**가장 중요한 결합 세 개**

1. **L1 × L3 = 성장.** P1의 물리적 표현. 질량이 변하면 실루엣이 변하고, 그 변화는 평형 사이에서만 확정된다.
2. **L2 × E1 = 경계의 이중 의미.** 경계는 정체성이면서 동시에 되돌릴 수 있음의 한계다. 시각 원시요소 하나가 두 층을 잇는다.
3. **L4 × L5 = 정직한 게으름.** 모르는 것을 모른다고 그리는 것이, 전부 파싱하지 않아도 되는 엔지니어링 허가가 된다.

## 6. 기각 · 병합한 개념

**법칙이 되지 못한 것을 명시하는 것이 이 문서에서 가장 중요한 부분이다.**

| 개념 | 판정 | 이유 |
|---|---|---|
| **ENTROPY** | **개명 → UNCERTAINTY** | 열역학 엔트로피는 *무질서*이지 *무지*가 아니다. 정보 엔트로피는 확률분포의 성질이지 "확인 안 됨"이 아니다. 유용한 아이디어(확신의 정도)는 살리고 **틀린 이름을 버렸다** |
| **GRAVITY (인력)** | **부분 기각 → MASS** | 질량은 유지. **상호 인력 시뮬레이션은 기각.** 물리 엔진이 필요해지고(§30 정지 조건), 배치가 매번 달라져 공간 기억이 무너진다. 질량은 **정렬하고 크기를 정할 뿐 끌어당기지 않는다** |
| **PENDULUM (진자 운동)** | **기각 (개념만 잔존)** | 흔들리는 애니메이션은 가짜 움직임이다. 진자에서 가져온 것은 운동이 아니라 **"멈추는 지점이 있다"** 는 개념뿐이고, 그것이 L3다 |
| **QUANTUM OBSERVATION** | **프레이밍 기각 → OBSERVATION 유지** | JuQode에서 관측은 **소프트웨어를 바꾸지 않는다.** 렌더링만 바꾼다. 양자역학과 구조가 다르다. 정직한 참조는 **지도학의 일반화**다 — 그리고 그쪽이 실제로 빌려 쓸 기법이 있어 더 유용하다 |
| **BECOMING (물리 법칙으로)** | **강등 → Product Philosophy P1** | 그 자체로는 *행동*을 규정하지 않는다. 믿음이다. 행동은 L1·L3가 담당한다 |
| **RESPONSIBILITY (물리 법칙으로)** | **이동 → Ethical Law E1** | 물리가 아니라 윤리다. 층을 섞지 않는다(§14 요구) |
| **KAFKA** | **법칙 아님 → 진단 렌즈 + P2** | 시각 법칙으로 만들면 장식이 된다. 진단 도구로 쓸 때 가장 강하다 |
| **NIETZSCHE 인용/초상** | **전면 기각** | 철학으로 제품을 장식하지 않는다 |
| **THERMODYNAMICS 일반** | **기각** | 소프트웨어는 닫힌계가 아니다. 에너지 보존도 열역학 제2법칙도 성립하지 않는다. 은유가 예측력을 갖지 못한다 |
| **Software Time = Git 커밋** | **기각 → 평형의 나열** | 커밋은 기술 사실이고 평형은 사람의 사실이다 (§10) |
| **7번째 법칙 후보 (REACH)** | **병합 → L2** | 외부 도달은 *경계를 통과하는 인과*다. 새 법칙이 필요 없다 |

**법칙 수 결산:** Philosophy 3 · Physics 5 · Ethics 2. §27 목표(2–4 / 4–6 / 1–3) 안에 있다.

## 7. 과학적 정직성 각서

이 문서는 물리학과 철학에서 **용어를 빌렸다.** 다음을 명시한다.

### 7.1 하지 않는 주장

> ❌ "양자역학이 UI가 이렇게 동작해야 함을 증명한다."
> ❌ "소프트웨어는 열역학 제2법칙을 따른다."
> ❌ "질량과 중력은 물리적으로 계산된다."

**전부 거짓이다.** 이 문서의 어디에도 그런 주장은 없다.

### 7.2 실제로 하는 주장

> ✅ 물리 개념에서 **설계 해석(design interpretation)** 을 가져왔다.
> ✅ 개념적 유비이며, 예측력은 **제품 안에서만** 성립한다.
> ✅ 유비가 틀린 곳에서는 **이름을 버렸다** (ENTROPY → UNCERTAINTY).

### 7.3 잘못된 이름을 실제로 버린 기록

| 원래 이름 | 문제 | 조치 |
|---|---|---|
| Entropy | 무질서 ≠ 무지. 유사과학이 될 위험 | **UNCERTAINTY로 개명** |
| Quantum Observation | 관측이 대상을 바꾸지 않는다 | **프레이밍 삭제.** 지도학 일반화로 참조 교체 |
| Gravity | 인력 시뮬레이션을 함의 | **MASS로 축소** |

> **명료함이 영리한 용어보다 중요하다.**
> 내부 이름이 오해를 부르면 그 이름을 버린다. 개념은 남는다.

### 7.4 사용자 노출 금지 어휘

`Software Physics` · `평형` · `엔트로피` · `질량` · `인과율` · `관측` ·
`Becoming` · 그 밖의 모든 법칙 이름.

**이 어휘들은 구현자와 PM의 것이다. 사용자의 것이 아니다.**
사용자는 `되돌아가기` · `확인됨` · `아직 확인 안 됨` · `모름` · `여기 바꾸면 저기가 같이 바뀝니다`를 본다.

## 8. Empty Software — 무엇인가

### 8.1 아닌 것

> ❌ "기능이 0개인 프로젝트"
> ❌ "아직 시작 안 한 상태"
> ❌ "채워야 할 빈 그릇"

### 8.2 법칙으로 본 Empty

| 법칙 | Empty에서의 값 | 함의 |
|---|---|---|
| L1 MASS | **0** | 내부 구조가 없다. 그러나 **경계는 있다** |
| L2 CAUSALITY | 경로 0 | 아직 아무것도 들어오거나 나가지 않는다 |
| L3 EQUILIBRIUM | **`SETTLED`** | Empty는 오류가 아니라 **정당한 평형이다.** 원점 평형 |
| L4 UNCERTAINTY | **0 — 완전한 확신** | 아무것도 없으므로 **틀릴 것이 없다** |
| L5 OBSERVATION | 해상할 것 없음 | FAR 하나로 충분하다 |
| E1 REVERSIBILITY | 위험 0 | 잃을 것이 없다 |

### 8.3 그래서 Empty란

> **Empty Software는 경계와 원점을 가지고, 질량이 0이며,
> 불확실성이 0인 — 완전히 알려진 유일한 평형 상태다.**

이 정의에서 두 가지가 따라 나온다.

**① 첫 Qode는 기능을 더하는 것이 아니라 불확실성을 도입하는 것이다.**
소프트웨어를 만드는 일은 **모르는 것을 만드는 일**이기도 하다. JuQode는 그것을 정직하게 그린다.

**② Empty 화면은 조용해야 한다 — 그것이 오류 상태가 아니라 완전한 상태이기 때문이다.**
온보딩 체크리스트나 제안 카드 6개는 *"당신은 아직 부족하다"* 는 잘못된 메시지다.
Empty는 부족한 상태가 아니다. **아직 아무것도 약속하지 않은 상태**다.

### 8.4 원점(origin)의 의미

원점은 장식이 아니라 **첫 번째 약속(first commitment)** 이다.
"여기에 소프트웨어가 있을 것이다"라고 사람이 정한 지점.

경계가 파선인 이유도 여기서 나온다 — **아직 하중을 받지 않았다.**
첫 Qode가 성공적으로 평형에 도달하면 경계가 실선이 된다.
이것은 3R.1 §4.4가 이미 규정한 동작이고, Canon이 그 *이유*를 준다.

### 8.5 낭만화하지 않기

Empty 화면은 여전히 **제품**이어야 한다. 시(詩)가 아니다.
사용자는 그 화면에서 **다음에 무엇을 할지 알아야** 한다.
그 역할은 Qode Composer가 한다 — 화면에서 유일하게 밝은 행동. 그것으로 충분하다.

## 9. Qode 상태 모델 — 작업 · 검증 · 실패

### 9.1 6개 상태. 이것이 전부다.

```
   SETTLED ──── Qode 시작 ───→ DISTURBED ──── 실행 완료 ───→ SETTLING
      ↑                            │                            │
      │                            │ 실행 실패                   │ 증거
      │                            ↓                            ↓
      │                        UNSETTLED               ┌──── SETTLED′
      └──── 이전 평형으로 ────────┴───────────────────┤
                                                      └──── UNKNOWN
```

| 상태 | 뜻 | 몸에서 |
|---|---|---|
| **SETTLED** | 안정. 지금 형태가 곧 사실이다 | 고요함. 실선 |
| **DISTURBED** | Qode가 시작됐다. 대상 영역의 안정성이 유예됐다 | **영향 영역만** 파선. 전역 스피너 없음 |
| **SETTLING** | 변경은 일어났으나 **아직 확인되지 않았다** | 새 구조가 보이되 `--attention`. 미확인 표기 |
| **SETTLED′** | 확인됐다. 새 평형 | 고요함 회복. **Software Time에 점이 찍힌다** |
| **UNSETTLED** | 확인 실패 | `--failure`. **이전 평형이 유효한 참조로 남는다** |
| **UNKNOWN** | 확인할 수 없었다 | 윤곽만. 거짓 성공으로 바꾸지 않는다 |

### 9.2 각 상태의 철학적 의미

**Qode가 실행 중이라는 것은 무엇인가?**
> 평형이 교란되었으나 **새로운 진실이 아직 성립하지 않았다.**
> 그래서 화면 전체가 아니라 *교란된 영역만* 안정성을 잃는다.

**실행은 끝났는데 검증이 안 됐다는 것은?**
> **`SETTLING`.** 코드는 바뀌었지만 그것이 사실인지 아직 모른다.
> 다른 도구들이 초록 체크를 주는 바로 그 지점이다. JuQode는 여기서 멈춰 서 있는다.

**검증이 실패했다는 것은?**
> **`UNSETTLED`.** 새 평형에 도달하지 못했다.
> 중요한 점: *이전 평형은 여전히 유효하다.* 사용자는 길을 잃지 않았다.

**되돌리기란?**
> 실행 취소가 아니라 **이전 평형으로의 복귀.**
> Software Time에 있는 점으로만 돌아갈 수 있다 — 즉 **확인된 상태로만** 돌아간다.
> "돌아갔더니 거기도 깨져 있더라"가 구조적으로 불가능해진다.

**`UNKNOWN`이란?**
> 실패가 아니다. **앎의 한계다.**
> 반드시 "무엇이 있으면 알 수 있는가"와 함께 제시된다(E2 완화 규칙).

### 9.3 이 모델이 만드는 제품 차이

| | 일반 에이전트 도구 | JuQode |
|---|---|---|
| 코드 작성 직후 | ✅ 완료 | `SETTLING` — 아직 아니다 |
| 테스트 못 돌림 | 조용히 완료 처리 | `UNKNOWN` — 명시 |
| 검증 실패 | ❌ 에러 로그 | `UNSETTLED` + 이전 평형 참조 유지 |
| 되돌리기 대상 | 커밋 목록 | **확인된 평형만** |

## 10. Software Time

### 10.1 기존 개념

`Git → Software Time`. 사용자 대면 행동은 사람의 말로 — `그때 보기` · `지금과 비교` · `여기로 돌아가기`.
Primary UI에 Git 용어 금지. **이 결정은 유지한다.**

### 10.2 Canon이 개선하는 지점

> **Software Time의 점은 커밋이 아니라 평형이다.**

| | 커밋 기반 | 평형 기반 |
|---|---|---|
| 점의 개수 | 수백 개 | 사람이 셀 수 있는 개수 |
| 점의 의미 | "누가 뭘 저장했다" | **"소프트웨어가 이런 상태였다"** |
| 돌아갈 수 있는가 | 깨진 커밋도 있다 | **확인된 상태만** 있다 |
| 만든 사람 | Git | **사용자의 Qode** |

### 10.3 은유를 강요하지 않는 지점

Software Time은 **평형의 나열**이지 물리적 시간이 아니다.
따라서 **속도 · 가속도 · 관성 같은 개념은 도입하지 않는다.**
유비가 유용한 데까지만 쓰고 거기서 멈춘다.

또한 JuQode 밖에서 일어난 변경(사용자가 직접 편집, 외부 커밋)은 평형을 만들지 않는다.
그것은 **교란**으로 들어오고 확인을 거쳐야 평형이 된다.
→ **Founder 결정 필요** (§16 D2)

## 11. 프로젝트 유형 스트레스 테스트

**요구사항: 유형별 렌더러를 만들지 않는다.** 유형은 법칙 값의 조합에서 *창발*해야 한다.

| 유형 | 질량 분포 | 인과 형태 | 경계 통과 | 특징적 확신 | 창발하는 실루엣 |
|---|---|---|---|---|---|
| **Empty** | 0 | 없음 | 없음 | 완전 | 경계 + 원점 |
| **Frontend** | 표면 집중 | 짧고 옆으로 많음 | 상단 1개 굵음 | 표면은 확인 쉬움 | 위가 넓다 |
| **Backend** | 중앙 집중 | 길고 아래로 · 분기 | 상단 + 측면 | 중앙 불확실 잦음 | 표면이 선으로 붕괴 |
| **Agent** | 중앙 집중 | **닫힌 회로** | **측면 다수** | 높음(비결정적) | 회로 + 강한 도달 |
| **Data** | 하부 집중 | 수렴 | 적음 | 낮음(구조가 명시적) | 아래가 무겁다 |
| **Full-stack** | 세 층 분산 | 관통 | 여러 방향 | 혼재 | 하나의 몸 |

**결론: 유형별 렌더러가 필요 없다.** 6개 유형 모두 (질량 분포 · 인과 형태 · 경계 통과 수 · 확신)
네 값의 조합이다. 3R.1이 이미 같은 렌더러로 6개를 그려 증명했다.

## 12. 비(非)웹 스트레스 테스트

**"웹 앱만 설명되면 FAIL"** — 요구사항 §17. 아래가 실제 검증이다.

| 유형 | 법칙으로 설명되는가 | 창발하는 형태 | 판정 |
|---|---|---|---|
| **CLI 도구** | 표면 = 호출 지점(작지만 0이 아님). 인과 = 선형. 통과 = stdin/stdout/파일 | 얇은 표면 + 선형 관통 + 하단 통과 | ✅ |
| **SDK / 라이브러리** | **경계가 뒤집힌다.** 스스로 나가지 않고 *남의 Port가 된다*. 인과가 바깥에서 안으로 | **표면 전체가 접촉면**. 바깥 도달 0 | ✅ **가장 흥미로운 케이스** |
| **컴파일러** | 인과가 지배적. 질량은 중앙. 통과 = 입력/출력 2개 | 깊고 긴 관통. 측면 도달 없음 | ✅ |
| **자동화 스크립트 모음** | **인과가 약하다.** 연결 없는 작은 질량 다수 | **줄기가 없는 흩어진 밭** — "이건 하나의 흐름이 아니다"가 정직하게 읽힌다 | ✅ |
| **인프라 프로젝트** | **질량이 경계에 있다.** 내부는 얇고 통과가 많다. E1 등급이 전반적으로 높다 | 경계가 두껍고 속이 빈 몸 | ✅ |
| **데스크톱 앱** | Frontend와 같되 통과 대상이 브라우저가 아니라 OS/파일시스템 | 위가 넓고 하단 통과 | ✅ |
| **게임** | 표면 질량 + **닫힌 회로(game loop)**. Agent와 같은 위상 | 넓은 표면 + 강한 회로 | ✅ |
| **모노레포** | ❗ **경계가 여러 개다** | — | ⚠️ **§16 D1** |
| **멀티 에이전트 오케스트레이터** | 중첩 회로 + 통과 다수 + 확신 낮음 | 회로 안의 회로 | ⚠️ 가독성 위험. 아래 참조 |
| **부분적으로 깨진 저장소** | `UNSETTLED` 영역 + 끊긴 경로 | 어딘가에서 끝나는 경로 | ✅ |
| **JuQode가 이해 못 한 저장소** | **L4 `모름` + L5 게으름** | **윤곽은 있고 내부는 비어 있다** | ✅ **결정적 케이스** |

### 12.1 SDK / 라이브러리 — 경계의 반전

라이브러리는 스스로 아무것도 시작하지 않는다. **누군가가 그것을 호출한다.**
법칙으로 보면 인과의 방향이 반대이고, 도달(reach)이 0이며, 표면 전체가 접촉면이다.

이것은 예외가 아니라 **같은 법칙의 다른 값**이다. 새 UI가 필요 없다.
그리고 이 형태는 그 자체로 유용한 사실을 말한다 —
*"이건 스스로 도는 물건이 아니라, 남이 쓰는 물건이다."*

### 12.2 JuQode가 이해 못 한 저장소 — P3의 진짜 시험

이것이 이 Canon 전체를 정당화하는 케이스다.

```
경계        그린다      — 파일이 있으니 무언가는 존재한다
질량        측정 가능한 만큼만 (크기·개수의 하한)
내부        그리지 않는다  — 모르기 때문에
확신        모름
```

화면은 라벨 없이 이렇게 말한다:

> **"여기 무언가 있다. 나는 아직 그 안을 모른다."**

IDE는 이 화면을 줄 수 없다 — 파일 트리는 **항상 뭔가를 아는 척**한다.
파일 목록은 구조가 아니지만 구조처럼 보인다. 그것이 IDE의 조용한 거짓말이다.

### 12.3 모노레포와 오케스트레이터 — 정직한 한계

**모노레포:** 하나의 몸이 아니다. 여러 개의 몸이 Port를 공유한다.
**권고: JuQode는 한 번에 하나의 Software를 렌더링한다.** 모노레포는 Software의 *집합*이다.
이것은 회피가 아니라 판정이다 — 하나로 그리면 반드시 거짓이 된다. → §16 D1

**멀티 에이전트 오케스트레이터:** 법칙은 성립한다(중첩 회로).
그러나 **가독성 위험이 실재한다.** 회로 안의 회로는 FAR에서 엉킨 실타래로 보일 수 있다.
완화책은 L5다 — FAR에서는 회로를 **하나의 덩어리로 접고**, MID에서만 편다.
**v0.1 대상이 아니다.** 검증되지 않은 완화책이므로 정직하게 표시해 둔다.

## 13. 운동(Motion) 규칙

### 13.2 Canon이 주는 검사

> **모든 애니메이션은 다음 질문에 답해야 한다: 어떤 실제 사건이 이것을 일으켰는가?**

### 13.3 허용되는 운동 — 법칙에 대응하는 것만

| 허용 | 대응 법칙 | 실제 사건 |
|---|---|---|
| 몸의 형태 변화 | L1 | 질량이 실제로 바뀌었다 |
| 경로 구간의 활성 | L2 | 그 구간에서 실제 실행이 일어나고 있다 |
| 영역의 안정/불안정 전환 | L3 | 평형 상태가 실제로 바뀌었다 |
| 모서리 품질 변화 | L4 | 증거가 실제로 도착했다 |
| 해상도 전이 | L5 | 사용자가 실제로 이동했다 |

### 13.4 금지 (HARD)

주변 입자 · 상시 부유 · 장식용 진자 · 전체 펄스 · 랜덤 물리 시뮬레이션 ·
로딩 셔머 · 등장 bounce · stagger · 병렬 처리 "느낌"을 내는 동시 애니메이션.

**특히:** 진자에서 L3를 가져왔다고 해서 **진자를 그리지 않는다.**
개념을 빌린 것이지 그림을 빌린 것이 아니다.

| **색** | E1 + L3만 | **결과 · 상태** | **범주. 절대 금지** |
| **밀도** | L1 | 복잡도 · 풍부함 | 정확한 개수 |

### 14.1 다음 단계가 반드시 답해야 할 질문

1. `SETTLING`을 **색 없이도** `SETTLED`와 구분되게 그릴 수 있는가? (색 예산이 좁다)
2. `모름`의 *내부를 그리지 않는* 표현이 FAR에서 "비어 있음"과 헷갈리지 않는가?
   → **Empty(질량 0, 확신 100%)와 모름(질량 있음, 확신 0%)은 반드시 달라 보여야 한다**
3. 전파 범위(L2)를 **애니메이션 없이** 정적으로 표현하는 방법은?
4. 경계 통과가 비가역을 뜻한다면, **가역적인 외부 읽기**(예: 조회 API)는 어떻게 구분되는가?

## 부록 B · 적대적 검토 (자기 공격)

각 법칙에 §28의 8개 질문을 던졌다. **약한 지점을 숨기지 않는다.**

| 법칙 | 가장 강한 반론 | 응답 | 남는 위험 |
|---|---|---|---|
| **L1 MASS** | "크면 중요하다"는 그냥 평범한 UX다. 법칙이 필요 없다 | 평범한 부분은 맞다. 법칙이 추가하는 것은 **질량의 정의를 파일 수로부터 금지**하고 **무게중심을 1급 읽을거리로** 만드는 것이다. 그 둘은 UX 상식이 아니다 | 구현자가 편의상 파일 수로 질량을 계산하면 법칙이 무의미해진다. **코드 리뷰 항목으로 강제해야 한다** |
| **L2 CAUSALITY** | 결국 화살표 그래프다. 플로차트와 뭐가 다른가 | 깊이 제한 · 경계 정지 · 의미 단위 제약이 없으면 **실제로 플로차트가 된다.** 제약이 법칙의 본체다 | 제약이 느슨해지는 순간 무너진다. 가장 취약한 법칙 |
| **L3 EQUILIBRIUM** | 그냥 "상태 기계"다. 철학이 필요 없다 | 상태 기계인 것은 맞다. 그러나 **`SETTLING`을 넣기로 한 결정**은 상태 기계가 주지 않는다. 그 결정은 "코드 작성 ≠ 완료"라는 입장에서만 나온다 | 사용자가 `SETTLING`을 "느린 제품"으로 오해할 수 있다. **표현이 관건** |
| **L4 UNCERTAINTY** | 확신 표시는 결국 노이즈가 된다 | **정당한 반론이다.** 그래서 노출을 3개 조건으로 제한하고, v0.1을 이진으로 축소했다 | 조건부 노출이 오히려 "가끔 나타나는 이상한 표시"가 될 수 있다. **3R.3에서 검증 필요** |
| **L5 OBSERVATION** | 유사 양자역학 브랜딩 아닌가 | **그 위험이 있었고, 그래서 양자 프레이밍을 삭제했다.** 지도학 일반화로 참조를 바꿨고 그쪽이 실제로 기법을 준다 | 없음. 개명으로 해소됨 |
| **E1 REVERSIBILITY** | 확인 모달을 철학으로 포장한 것 | 모달이었다면 그렇다. 그러나 **"경계 = 되돌릴 수 있음의 한계"** 는 시각 원시요소에 의미를 주는 구조적 발견이다. 모달은 그 결과 중 하나일 뿐 | 구현이 결국 모달로 수렴할 위험. **몸에서의 표현이 먼저여야 한다** |
| **E2 EVIDENCE** | 아무것도 확인 안 되면 제품이 마비된다 | **가장 현실적인 위험.** 완화 규칙(`UNKNOWN`은 행동 가능해야 한다)으로 대응 | Evidence 파이프라인이 약하면 제품이 온통 `SETTLING`이 된다. **Phase 4·6의 실질적 위험** |

### 기각한 법칙에 대한 자기 검토

**"Becoming을 물리 법칙에서 뺀 것이 옳은가?"**
Becoming이 규정하는 행동(완성도 지표 금지 · 재정규화)은 전부 L1·L3로 표현된다.
별도 법칙으로 두면 **중복**이고, §27이 중복을 금지한다. 강등이 옳다.

**"법칙이 5개면 충분한가, 아니면 뭔가 놓쳤는가?"**
가장 그럴듯한 6번째 후보는 **COMPOSITION**(소프트웨어는 소프트웨어로 이루어진다)이었다.
모노레포·라이브러리 케이스가 이것을 요구하는 것처럼 보인다.
그러나 §16 D1이 "한 번에 하나만 렌더링"으로 답하는 순간 **v0.1에서는 불필요**해진다.
**보류로 기록한다** — Canon에 넣지 않되, 미래에 필요해질 것으로 명시한다.

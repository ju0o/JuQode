# MVP Wireframe — Freeze

> **Status:** 구현 직전 최종 제품 설계. 새 철학·표상·Realm을 만들지 않는다.
> **Board:** [`mvp-wireframe.html`](mvp-wireframe.html) · 근거 이미지 `evidence/mvp-wireframe/`
> **Lovable calls:** 0. 구현하지 않는다.

## 1. 유지되는 것 (변경 없음)

Software World = 주 인터페이스 · `SEE → POINT → SAY` ·
Qode = Software + 관측 + 대상 + 의도 · Context = 자동 준비 · RUN = 관측 ·
결과는 Outcome-first · 파일/코드 = 깊은 기술적 사실 ·
상시 파일 트리 · 터미널 · 대화 기록 · 컨텍스트 관리자 **없음.**

## 2. MVP가 더하는 것 하나 — 문제 모듈

> **World는 현상을 보여주고, 문제 모듈은 그것을 사람 말로 설명한다.**

추상만으로는 부족하다. 결이 붉게 어긋나 있는 것을 보고도
"그래서 뭐가 문제인데?"에 답하지 못하면 제품이 아니다.

```
현재 문제 2                                          전부 보기
결제 요청              │  사용자 저장
응답이 늦어요           │  가끔 목록이 비어요
```

**규칙**

| | |
|---|---|
| 제목 먼저 | 자리 이름이 제목이다. 설명은 한 줄 |
| 사람 말 | 스택 트레이스도 로그도 아니다 |
| 자리에 매여 있다 | 모든 문제는 **실재하는 의미의 자리**를 가리킨다 |
| 누르면 잡힌다 | World의 그 자리가 스스로 또렷해지고 입력 문장이 바뀐다 |
| 얇다 | 두 줄. 사이드바도 대시보드도 로그 목록도 위젯도 아니다 |
| 사라진다 | 문제가 0이면 모듈도 없다 |

**색은 상태에만 쓴다(기존 법칙 유지).** 문제의 경중은 색이 아니라 **결의 거동**이 말한다.

```
연결이 끊겨요   →  결이 끊긴다   (양쪽 결이 만나지 못함)
응답이 늦어요   →  결이 어긋난다 (이어져 있으나 주위와 안 맞음)
```

## 3. 상호작용

```
문제 모듈  →  World Focus  →  Qode
```

```
"결제 요청"을 누른다
  → World에서 결제 요청 자리가 또렷해지고 이름이 뜬다
  → 입력이 바뀐다: "결제 요청 문제에 원하는 변화를 말해보세요."
  → 사용자는 "이거 고쳐줘" 라고 친다
  → 맥락은 이미 준비되어 있다
```

실패가 명백할 때는 입력이 **"고쳐줘"** 한 마디로 충분하다.

## 4. MVP 범위 컷

시각적으로 **Realm 하나만** 쓴다 — 현재의 결(Field/Grain).
Ocean · Newton · Kafka · Agent Realm은 **설계하지 않는다.**
구조만 미래 Realm과 호환되게 남긴다(자리 · 질량 · 상태 · 증거는 Realm 독립).

## 5. 여덟 화면

| | 무엇을 증명하는가 |
|---|---|
| **01 Launcher** | 열기 전에 이미 **문제가 몇 개인지** 안다. 저장소 용어가 주 언어가 아니다 |
| **02 Workspace** | World가 압도한다. 문제 모듈은 두 줄. 상단 다섯 단어 · 하단 한 줄이 전부 |
| **03 Problem → Focus** | 화살표도 연결선도 없이 **문제와 자리가 이어진다** |
| **04 Qode · Context** | 양식이 아니다. 문제 하나 누르고 세 글자 치면 끝 |
| **05 Working** | 진행률 막대 없음. 교란된 자리만 흔들리고 실제로 하는 일 한 줄 |
| **06 Result** | 몸이 먼저 가라앉고 글자가 확인한다. 문제 **2 → 1** |
| **07 Run → New Problem** | **MVP의 핵심 순환.** 실행이 관측으로 들어와 문제 한 줄이 늘고 "고쳐줘"로 이어진다 |
| **08 Deep View** | 목록의 머리에 "세션 유지 —"가 붙어 있다. IDE로 돌아가지 않는다 |

## 6. 화면 골격 (동결)

```
┌ 상단 한 줄 ── 이름 · 상태 · 시간 실행 가져오기 연결 깊이 ┐
│                                                        │
│                    SOFTWARE WORLD                      │
│                     (가장 큰 것)                        │
│                                                        │
├ 문제 모듈 (문제가 있을 때만, 두 줄) ─────────────────────┤
├ 도구 판 (필요할 때만, 한 줄) ───────────────────────────┤
└ 입력 한 줄 ─────────────────────────────────────────────┘
```

부차 행동 — `가져오기` `연결` `시간` — 은 **상단의 단어 하나**로만 존재한다.
이 단계에서 전용 화면을 만들지 않는다.

## 7. 이 판이 답하는 질문

어디를 보나(World) · 어디를 누르나(문제 모듈) · 어디에 치나(아래 한 줄) ·
문제는 어떻게 나타나나(World의 결 + 모듈 한 줄) · Qode는 어떻게 시작되나(문제 → 자리 → 말) ·
일하는 동안 무엇이 보이나(교란된 자리 + 한 줄) · 무엇이 돌아오나(Outcome + 확인됨) ·
기술적 사실엔 어떻게 닿나(깊이, 자리에 매인 채로).

## 8. 미해결 (MVP 이후)

1. **여러 Qode 동시 진행** — `남은 문제 n`만 표시했고 병렬 작업 화면은 없다
2. **문제가 10개 이상**일 때 모듈이 두 줄로 버티는지 — `전부 보기`의 확장 화면 미설계
3. **문제의 출처** — 실행 관측 외에 정적 분석·테스트·사용자 신고를 어떻게 합칠지
4. **Realm 전환** — 한 Software 안에서 서로 다른 현상이 어떻게 이어지는지
5. **자리 수용량** — 또렷이 구분되는 자리 5~7개 한계가 그대로 남아 있다
